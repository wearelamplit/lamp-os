# Lamp OS networking reference

This document describes the communication protocols that move data between the
lamps, the wisp infrastructure node, the Flutter app, and the Straylight
palette feed (OSC) — the **ESP-NOW mesh** between lamps, the **BLE GATT** link to the phone,
and the firmware-distribution messages. It is the authoritative wire-format
reference; if code and this doc disagree, the code wins and this doc should be
updated.

## Message tier overview

Four behavioral tiers, each with its own crypto posture, reach, and lifetime:

| Tier | Reach | Crypto | Lifetime | Examples |
|---|---|---|---|---|
| **Presence** | Broadcast (lamp: 30s, wisp: 2s) | Plaintext | None, pure state report | `MSG_HELLO`, `MSG_WISP_HELLO` |
| **Wisp control** | Unicast (lamp → wisp) or broadcast (wisp → lamps) | Sealed wispOp OR plaintext JSON | Wisp-side NVS; lamps only cache what the wisp reports | `MSG_CONTROL_OP` |
| **Transient overrides** | Unicast (broadcast for restore) | Plaintext | RAM-only; watchdog-released after 60s | `MSG_OVERRIDE_BRIGHTNESS/RESTORE_BRIGHTNESS` (space-dim). Wisp paint no longer rides `MSG_OVERRIDE_COLORS/RESTORE_COLORS`; it's declared in `MSG_WISP_STATE`. |
| **Expression announce / directed** | No relay: EVENT nearby-broadcast, COMMAND targeted (addressedToUs filter on recv) | 8-byte HMAC-SHA256 shared-key tag (`command_auth`) | RAM-only; observer-delivered / applied | `MSG_EVENT`, `MSG_COMMAND` |

**Relay policy:**

| msgType | Reach | Relay? | Storm bound |
|---|---|---|---|
| `MSG_HELLO` (0x01) | broadcast | yes, gossip-rebroadcast, counter-suppressed (see below) | `helloDedup_` 64-slot ring per (sourceMac, seq), which a lamp's own HELLO echoed back by a relayer never enters (`admitHello`) + `HelloRelaySuppressor` 16-slot pending table |
| `MSG_CONTROL_OP` (0x03) | unicast or broadcast | yes, whatever the target, staggered (see below) | `controlOpDedup_` 64-slot ring + `controlRelay_` 2-slot stagger table |
| `MSG_WISP_HELLO` (0x20) | broadcast | one hop, relayed only when heard direct from the wisp, staggered | `wispHelloDedup_` 32-slot ring + `wispRelay_` 4-slot stagger table |
| `MSG_WISP_CLAIM` (0x25) | broadcast | **no**, direct radio range only | `wispClaimDedup_` 16-slot ring |
| `MSG_WISP_PALETTE` (0x26) | broadcast | one hop, relayed only when heard direct from the wisp, staggered | `wispPaletteDedup_` 32-slot ring + `wispRelay_` (shared with WISP_HELLO) |
| `MSG_WISP_PAINT` (0x27) | broadcast | **no**, ignored on receive | n/a — **retired**, wisp no longer emits it; STATE carries per-lamp colors |
| `MSG_WISP_STATE` (0x28) | broadcast | **no**, direct radio range only | `wispStateDedup_` 16-slot ring — sole wisp paint render path |
| `MSG_OVERRIDE_COLORS` (0x21) | unicast | **no**, single-hop, addressedToUs filter | n/a (no relay) — **retired** as the wisp paint path; parser kept, no sender |
| `MSG_RESTORE_COLORS` (0x22) | unicast or broadcast | **no**, single-hop | n/a — **retired**, STATE-absence eases a lamp home |
| `MSG_OVERRIDE_BRIGHTNESS` (0x23) | unicast | **no**, single-hop | n/a |
| `MSG_RESTORE_BRIGHTNESS` (0x24) | unicast or broadcast | **no**, single-hop | n/a |
| `MSG_EVENT` (0x30) | broadcast | **no**, single-hop nearby-only | `eventDedup_` 32-slot ring |
| `MSG_COMMAND` (0x31) | broadcast (physical); addressedToUs filter on recv | **no** | `commandDedup_` 64-slot ring |
| `MSG_COLOR_QUERY` (0x32) | broadcast (physical); addressedToUs filter on recv | **no** | n/a (single-hop) |
| `MSG_COLOR_INFO` (0x33) | broadcast (physical); addressedToUs filter on recv | **no** | n/a (single-hop) |

Relay rule: every lamp that successfully parses + dedup-records a relayable frame AND is not the originator (self-MAC drop) rebroadcasts the frame verbatim, at most once (a staggered copy can be dropped late, below), whatever application-level filtering then does with it. `MSG_CONTROL_OP` relays whatever its target. Local apply never waits on the relay.

Every relay that fits its table waits a per-lamp delay first, from one function, `relayDelayMs` (`components/network/mesh/relay_delay.hpp`): a hash of the relayer's own MAC and the frame's `(sourceMac, msgType, seq)`, mapped into the type's window. Lamps that heard the same frame therefore rebroadcast it at different moments, and the offset between any two lamps changes from frame to frame, so no pair collides on every frame (a per-frame delay plus a fixed per-lamp phase would lock each pair's offset).

The wisp's frames (`MSG_CONTROL_OP`, `MSG_WISP_HELLO`, `MSG_WISP_PALETTE`) relay through `RelayStagger` (`relay_stagger.hpp`) over a 0 to 150 ms window (`kRelayStaggerWindowMs`). Two copies started uniformly in it overlap with odds of about 2 x airtime / window: 1.7% for a WISP_HELLO (1.3 ms), 5.7% for a status plus palette (4.3 ms). The recv task copies the frame into a free slot; the loop sends it when due, only while a TX credit is ready (`MeshLink::txReady`), as the cascade drain does, so a credit stall waits instead of hammering the driver. A submit that fails with a credit ready is a driver error, retried next pass. A copy still unsent 1 s (`kMaxRelayLateMs`) after its fire time is dropped and counted in `dropped`, whatever held it: a credit stall, a failing driver, or an unannounced loop stall over 1 s. A known loop stall queues nothing: while the loop runs a known multi-second block (the OTA receiver's upfront erase, the BLE teardown for the web app, each held by `KnownLoopStall` in `util/loop_stall.hpp`), enqueue fails open and the copy relays inline at once on the recv task. Copies queued before the block are serviced when it ends, and are dropped like any other if the block outlasts the 1 s cap. The cap is half the 2 s between statuses in an op's burst: a seconds-late status could land after a newer one and roll a lamp's cached status back. A full table (2 control slots, 4 for WISP_HELLO and WISP_PALETTE, enough for two wisps) or a frame over the slot size relays inline at once, refused and lost like any send when no TX credit is free. A reboot loses what is queued, at most 6 frames. The delay is receive-side only: wire bytes, dedup and relay scope are unchanged, and older lamps that relay inline interoperate. Nothing downstream notices 150 ms (app confirm windows, the 22 s source guard, the 12 s sticky slot); the 250 ms status/config gap that older lamps need (see the wispConfig cadence) keeps the two in order, never reversed, while the `[relaystagger]` `maxlate` stays at or under 100 ms, the bench pass bar: the worst pair at such a lamp, a status first heard by relay at 150 ms plus `maxlate` and a config heard direct at 250 ms, lands 100 ms less `maxlate` apart. At the bar that is about 0 ms, so the two can share one loop pass at such a lamp and the status can be lost.

`MSG_HELLO` relay is **counter-suppressed** (receive-side only, no wire change). A first-seen HELLO is not relayed immediately; `HelloRelaySuppressor` enqueues it in a 16-slot pending table keyed on `(sourceMac, seq)` with a fire delay over `kHelloRelayJitterMinMs`..`kHelloRelayJitterMaxMs` (50 to 200 ms) from `relayDelayMs`, so it differs between neighbours and lets first-ring relayers hear each other's copies before firing. Every duplicate `(sourceMac, seq)` heard before the delay elapses — the frames that `helloDedup_` would otherwise silently drop — increments that entry's `dupCount`; each duplicate is one neighbor that already relayed the beacon. At fire time (`MeshLink::tick`) an entry with `dupCount >= kHelloSuppressThreshold` (3) is dropped, since the mesh already covered it; otherwise the stored frame is relayed verbatim, refused like any send when no TX credit is free. This pulls total HELLO airtime down from ~N²/interval (every node relaying every beacon) toward the coverage the mesh actually needs, without RSSI gating. Table overflow **fails open** (relay immediately) so a full table never suppresses a relay. A suppressing node simply transmits less; old-firmware peers that relay unconditionally still interoperate, and the relayed bytes are byte-identical to what arrived. Under `LAMP_DEBUG` each lamp prints a 30 s `[hellosupp] win=30s suppressed=N relayed=M rate=XX%` line (piggybacked on the `[meshmix]` window) so the kill rate is directly observable on the bench. `MSG_WISP_HELLO` and `MSG_WISP_PALETTE` relay one hop: a lamp rebroadcasts them only when the frame transmitter equals the originator wisp (heard direct), so a relayed copy (`srcMac != sourceMac`) is not re-relayed. This carries wisp presence/palette to lamps one hop past the wisp's own radio range so the app's wisp view converges across paired lamps despite coex-dropped broadcasts, while bounding propagation to exactly one hop. Remaining wisp traffic (`CLAIM`, `STATE`, `OVERRIDE_BRIGHTNESS`) stays direct-only. Per-message-type `DedupRing` instances (separate per msgType, each sized to its traffic — 64 slots for relay-heavy types, fewer for single-hop / low-rate ones) bound the storm to ≤ N relays per cascade in an N-lamp mesh.

`OVERRIDE_BRIGHTNESS` / `RESTORE_BRIGHTNESS` deliberately stay single-hop. They're unicast by design (`esp_now_send(targetMac, ...)` with 802.11 driver-level retries; per-link reliability is already strong). Gossip-relay would amplify airtime without obvious benefit because non-addressed receivers drop after the relay step anyway.

## ESP-NOW message catalog

Every frame starts with the same 6-byte header:

```
[MAGIC_0='L'(1)] [MAGIC_1='M'(1)] [PROTOCOL_VERSION(1)] [msgType(1)] [seq(2 LE)]
```

The wire carries a **receive range**, not a single version: `PROTOCOL_VERSION_EMIT = 0x05` is what a node broadcasts; `RX_MIN = 0x04` .. `RX_MAX = 0x05` is what it parses. Splitting emit from receive lets the fleet *receive* a newer version before any node *emits* one — the safe path for a multi-version OTA wave, where mixed versions coexist as long as every node's RX range covers what its peers emit. The v0x05 emit carries a TLV trailer on HELLO + WISP_HELLO (TLVs: `HELLO_TLV_OTA_STATE`, `HELLO_TLV_FW_CHANNEL`, `HELLO_TLV_FS_STATE`, `HELLO_TLV_FW_MAX_CHUNK`, `HELLO_TLV_OTA_SENDING_TO`, `HELLO_TLV_VARIANT`); v0x04 frames omit it and parsers accept both. Per-message-type DedupRing capacities are sized per traffic (receive-side state, not a wire contract — a resize needs no version bump) and the HELLO interval is 30 s. Bump the version only for a genuine parser-contract change — additive fields ride as TLVs (unknown TLVs are skipped, forward-compat). `inspect()` rejects a frame whose version falls outside `[RX_MIN, RX_MAX]`, so a node emitting outside the fleet's range silently stops showing up — a loud, diagnosable failure by design. The **wisp** is the standing hazard here: it's OTA-excluded, so it never moves forward on its own and goes invisible on the mesh after a bump pushes emit past its RX window, until it's hand-flashed.

**Reserved bits** (must be 0; receivers reject any frame that sets them):

- `kReservedMsgTypeHighBit = 0x80` on the `msgType` byte (`data[3]`). `inspect()` does not mask the bit, so any frame that sets it surfaces as an unknown msgType.

### Sequence numbers and dedup

The header `seq` names a frame for dedup. It carries no order: a receiver compares seqs only for equality (the `(sourceMac, msgType, seq)` dedup key, and an ACCEPT's `offerSeq` against the offer it answers), and nothing may depend on a seq's order or its start value. A counter that something must read in order is a separate field, such as the wisp's `opSeq`.

- **Senders start each boot at random.** Every counter a node stamps on frames it originates is a `SenderSeq` (`lampos/protocol/sender_seq.hpp`), which takes its start from `esp_random()` on its first frame of the boot, then counts up and wraps at 0xFFFF. Relayed frames keep the originator's seq. The counters: on the lamp, `MeshLink`'s HELLO, CONTROL_OP, COMMAND, EVENT, COLOR_QUERY and COLOR_INFO; each `FirmwareDistributor` (firmware and FS) for its OFFER, CHUNK and DONE; each `FirmwareReceiver` (firmware and FS) for its ACCEPT, REQ and RESULT. On the wisp, `SeqSource`, shared by WISP_HELLO, WISP_CLAIM, WISP_STATE, WISP_PALETTE and its own CONTROL_OPs, and `PaintDistributor`'s OVERRIDE_BRIGHTNESS. A new frame type takes a `SenderSeq`, never a counter that starts at a fixed value.
- **Receivers forget after 20 s.** A `DedupRing` drops a tuple it recorded within `kDedupMaxAgeMs` (20 s) and takes it as new after that, on top of evicting the oldest tuple when full. Legitimate repeats land well inside the age: resend copies within 80 ms, a relay copy at most 150 ms plus 1 s late per hop, OFFER retries within about 2 s.
- **Why both.** Older firmware starts these counters at 0 every boot (all but the lamp's HELLO and the wisp's `SeqSource`), and its rings never age a tuple. Older lamps (1.3.4 and earlier) also record a broadcast FW_OFFER or FS_OFFER before checking its target, so every lamp in range burns each offer seq, whoever it was addressed to, until 16 newer firmware-family frames push it out. A current lamp records a firmware-family frame (`MSG_FW_*`, `MSG_FS_*`) only once its target is this lamp or broadcast (`admitAddressed`, `components/network/mesh/frame_admission.hpp`), so another lamp's session never takes a slot in its `firmwareDedup_`. A seed lamp that restarted at 0 had every OFFER after a reboot dropped silently by those lamps, with no ACCEPT and no decline, and a relaying lamp's wisp ops were dropped at the wisp after it rebooted until its seq passed the old range. A random start keeps a current sender clear of the tuples older receivers still hold: a new boot collides only if its start lands inside the range an older boot left behind, odds of about the held frame count in 65536. The age bounds what a current receiver loses to an older sender's restart to 20 s from that sender's last frame before it.

### Tier 1: Presence

**`MSG_HELLO` (0x01)**, Lamp presence beacon. Broadcast by every lamp every 5 s for the first 30 s of uptime (boot burst, so a missed first HELLO refills the roster in seconds), then every 30 s. Pruned from `lampRoster` after 240 s of silence.
```
header(6) + sourceMac(6) + shade[4 RGBW] + base[4 RGBW] +
firmwareVersion(4 LE) + nameLen(1) + name[0..32] +
tlv_count(1) + TLV trailer (v0x05+)
= 26..93 bytes
```
`shade` and `base` each carry their gradient's blended-identity color (`lampos::led::blendedIdentity`), a linear-light weighted blend of all stops rather than a single indexed stop.

TLV trailer (v0x05+): `tlv_count(1)`, then per TLV `type(1) + len(1) + value(len)`:
- `HELLO_TLV_OTA_STATE` (0x01), len 1: 0=idle / 1=sending / 2=receiving. Emitted only when non-idle.
- `HELLO_TLV_FW_CHANNEL` (0x02), len 16: this lamp's `{type}-{channel}` identity (e.g. `standard-beta`, zero-padded) — same string as the LSIG footer + `MSG_FW_OFFER` channel. The distributor uses it via `otaAcceptable` to gate offers (see Channel promotion below).
- `HELLO_TLV_FS_STATE` (0x03), len 8: first 8 bytes of the peer's FS-image manifest digest. Used by FS-OTA to detect peers whose filesystem image differs from the distributor's.
- `HELLO_TLV_FW_MAX_CHUNK` (0x04), len 2: this lamp's largest acceptable `MSG_FW_CHUNK` payload (LE, `FW_CHUNK_SIZE_MAX` = 1444). The firmware distributor negotiates the session's chunk size from it: `min(FW_CHUNK_SIZE_MAX, peer's advertised value)` when present, else `FW_CHUNK_SIZE_BASELINE` (200) — the floor every OTA receiver, old or new, accepts.
- `HELLO_TLV_NEED_FS` (0x05), len 1: set when this lamp is FS-capable but has no valid local FS digest (SPIFFS empty/unmountable), so it can't emit `HELLO_TLV_FS_STATE`. Distinguishes "needs an FS image" from "legacy/FS-disabled" so the FS distributor offers to it (the offer is version-coupled to the distributor's firmware, which the peer already runs). Re-evaluated every HELLO; cleared once a valid FS is present.
- `HELLO_TLV_OTA_SENDING_TO` (0x06), len 6: the mesh MAC of the peer this lamp is currently OTA-distributing firmware to. Emitted only while sending (single-peer distributor), alongside `HELLO_TLV_OTA_STATE` = sending. Lets the app name the send edge and mark the receiver, which is HELLO-silent during its own OTA. Absent on idle lamps and older firmware.
- `HELLO_TLV_VARIANT` (0x07), len 1: the sender's `LampVariant` — `Unknown=0, Standard=1, Snafu=2, Staff=3, Lioness=4, Loaf=5` (append-only; a new variant takes the next value). Lets a variant-aware behavior react to what kind of lamp a peer is (surfaced as `PeerView::variant`). Absent on legacy / BLE-only peers, which read as `Unknown`. Additive TLV — **no `PROTOCOL_VERSION` bump** (unknown TLV skipped by older parsers).

Unknown TLV types are skipped by length (forward-compat); a receiver that doesn't know a type just gets the default for that field.

**`MSG_WISP_HELLO` (0x20)**, Wisp presence beacon. Broadcast by wisp every 2 s. A FreeRTOS software timer flags the emit due on the 2 s cadence; `PresenceBeacon::pump()` on the loop task does the build + broadcast, off the 2 KB timer stack (so a busy loop pass delays the actual send). Liveness only: presence, version, and flags for the app. It does not hold a lamp's colour paint alive — that hold rides `MSG_WISP_STATE` freshness (see `MSG_WISP_STATE` below).
```
header(6) + sourceMac(6) + wispVersion(4 LE) + flags(1) +
paletteIdPrefix(8 utf-8, null-padded) +
carriedFwChannel(16 utf-8, null-padded) + carriedFwVersion(4 LE) +
tlv_count(1) + TLV trailer (v0x05+)
= 45 bytes fixed (WISP_HELLO_FIXED_SIZE); wisp emits 46 (tlv_count=0),
  cap WISP_HELLO_MAX_SIZE = 96
flags bit 0 = paintMode, bit 1 = wifiConnected, bit 2 = sourceLive
```
Bit 2 (`WISP_HELLO_FLAG_SOURCE_LIVE`) is the same signal as wispStatus
`sourceLive`: Osc mode and a non-blank palette held from the OSC target;
for Straylight, also something from its feed within the last 30 s. It reuses the bit position the retired
Aurora source used for "connected", with no protocol version bump: no
receiver gates on bit 2 (lamps ignore the flags byte; the app reads the same
signal from wispStatus `sourceLive`, and `helloFlags` is only passed through),
so no parser contract changed.
The TLV trailer shares HELLO's shape (`tlv_count(1)`, then `type(1) + len(1)
+ value(len)` per TLV); the wisp emits `tlv_count=0` and the parser skips
unknown types by length (forward-compat).
- **Sender**: wisp(s) only. Lamps adopt into the display slot on receipt, whether heard direct or via a one-hop relay; only a direct frame is re-relayed (one hop). Lamps never originate.

**`MSG_WISP_CLAIM` (0x25)**, Wisp claim broadcast: the lamps this wisp currently paints, at the RSSI it hears each one. Peer wisps consume it for boundary arbitration; lamps accumulate the entries for `CHAR_WISP_CLAIMS` and display-slot admission.
```
header(6) + sourceMac(6) + count(1) + entries[count*7]
  entry: lampMac(6) + int8 rssi(1)
= 13..713 bytes  (count ≤ kMaxWispClaimEntries = 100)
```
- **Sender**: wisp(s) only, keyed to the 2 s presence tick. `CLAIM` goes out with the HELLO on odd ticks (every ~4 s). `MSG_WISP_STATE` goes out every tick (~2 s) at a random 200 to 800 ms offset after the HELLO, in a loop pass of its own, so two fat frames never go out in one pass on the single core (see `MSG_WISP_STATE` cadence). A paint-mode edge also emits `MSG_WISP_STATE` out of cadence for a prompt on/off. No gossip relay (direct radio range only).
- **Full-set frame**: one v2 frame carries the whole claim set (up to `LampInventory::MAX_LAMPS` = 100 = the receiver's `WispFleetCache` capacity), so every claimed lamp refreshes each tick — no windowing, no rotation cursor. Past 100 claimed the extras are truncated cleanly (unreachable on one wisp).
- **Admission**: a wisp claims every lamp it directly hears (a real RSSI measurement). Lamps it never hears itself are never claimed. A relayed HELLO keeps a lamp in the inventory but never refreshes its RSSI, and the inventory forgets a direct RSSI older than `kDirectRssiMaxAgeMs` (three lamp HELLO intervals, 90 s; `fleet/lamp_inventory.hpp`) at its next 30 s prune, so it lapses 90 to 120 s after the last direct HELLO. A claimed lamp with no current direct RSSI stays claimed only while no peer wisp claims it with a real RSSI, and is advertised with RSSI `INT8_MIN`, which peers ignore. A lamp that moves out of one wisp's radio range is handed to a wisp that still hears it; a lone wisp keeps a lamp that goes HELLO-silent (an OTA receiver) until the 240 s prune.
- **Arbitration**: peer entries age out after 20 s of silence (`WISP_ROSTER_PEER_AGE_MS`); ±5 dB RSSI hysteresis with last-owner stickiness; lower MAC wins a simultaneous-claim tiebreak.

**`MSG_WISP_PALETTE` (0x26)**, Wisp's canonical manual palette, broadcast for app convergence. The wisp is the source of truth for the manual palette so the same operator gets the same view regardless of which paired lamp they're talking to.
```
header(6) + sourceMac(6) + count(1) + rgb[count*3] + w[count]
= 13..213 bytes  (count ≤ kMaxWispPaletteColors = 50)
```
- **Sender**: wisp(s) only. Lamps cache on receipt (dedup ring `wispPaletteDedup_`) and re-relay one hop only when heard direct; they never originate.
- **Cadence**: piggybacked on the existing 30 s `emitStatus()` tick, emitted right after `MSG_CONTROL_OP wispStatus` in the same broadcast pass. Also fired on `triggerOnChange()` after a `setManualPalette` wispOp, so app edits propagate within ~2 s.
- **Encoding**: a packed R, G, B block followed by a per-color W plane. The plane is a length-gated trailer: `parseWispPalette` accepts frames longer than `count*3` (it always has), so parsers that read only the RGB block skip it, and frames without it parse with `w == nullptr` (W reads as 0). W is **warm white** — the lamp grid's dedicated warm emitter, "amber" in ArtNet fixture terms. RGB-only surfaces (the wisp's WS2812 ring, the app's gradient bar) fold W back into RGB with the shared warm-bias math.
- **Manual only**: the frame carries the stored manual palette in every source mode, at most 16 colors from a wisp that caps it (see `setManualPalette`). An OSC palette is never broadcast here, so in Osc mode the app has no copy of the live palette beyond `paletteIdPrefix`.
- **Lamp-side cache**: each lamp stores the latest `(mac, rgbw[], count)` in `LampRoster::WispCache.manualPaletteRgbw` (interleaved R,G,B,W). The app reads it raw from the `wisppalette` page section (see the page protocol below), off the status, whose frequent palette-less notify would clobber it.

**`MSG_WISP_PAINT` (0x27)**, **retired**. The wisp no longer emits it; `MSG_WISP_STATE` carries the same per-lamp base/shade colors and feeds the app's "Painted lamps" preview. The wire format (`header(6) + sourceMac(6) + count(1) + entries[count*12]`, entry `lampMac(6) + baseRGB(3) + shadeRGB(3)`) stays documented and the type ID stays reserved, because a wisp older than beta-1.1.8 still broadcasts it. A lamp ignores the frame on receive: no parse, no dedup, no slot.

**`MSG_WISP_STATE` (0x28)**, Declarative per-lamp state: base+shade per claimed lamp plus the wisp's per-frame globals — the **sole** wisp paint render path. A lamp gates the frame to its display wisp (`sourceMac` match), then scans for its own mesh MAC: on a hit it edge-triggers the eased wisp `LayerStack` base/shade targets and holds presence; on a miss in a fresh frame (Off, or unclaimed) it eases home promptly. Every entry also feeds the app's painted-lamps preview (`WispFleetCache`), the role `MSG_WISP_PAINT` used to fill. Each entry carries the lamp's colors as they stand when the frame is built, so during a drift step's fade (see Paint hold below) successive frames walk the lamp toward its new color; the drift fade trailer below lets a lamp run the fade itself instead. `brightness` / `driftRateMs` are carried but not yet consumed by the lamp render path (space-dim still rides `MSG_OVERRIDE_BRIGHTNESS`).
```
header(6) + sourceMac(6) + brightness(1) + driftRateMs(4 LE) +
presenceFlags(1) + count(1) + entries[count*12] + w[count*2]
  entry: lampMac(6) + baseRGB(3) + shadeRGB(3)
  w:     baseW(1) + shadeW(1) per entry, in entry order (WISP_STATE_W_SIZE)
+ optional TLV trailer (only after a W plane):
  [tlv_count(1)] [type(1) len(1) value(len)] × tlv_count
= 19..1470 bytes  (count ≤ WISP_STATE_MAX_ENTRIES = 103, ≤ ESPNOW_V2_FRAME_MAX)
```

| TLV | Type | Value |
|---|---|---|
| `WISP_STATE_TLV_DRIFT_FADE` | 0x10 | records, `WISP_STATE_DRIFT_FADE_RECORD_SIZE` (11) bytes each: `entryIndex(1)` (into this frame's entries) + target base RGBW(4) + target shade RGBW(4) + `leftDs` u16 LE (time left in the fade, 100 ms units, rounded up). At most 23 records per TLV; more repeat the type. |
| `WISP_STATE_TLV_DRIFT_FADE_PARTIAL` | 0x11 | len 0. The frame's records cover only some of the entries mid-fade. |

The type ids share HELLO's 1-byte TLV registry (`presence.hpp`), outside its 0x01..0x07. A parser that stops at the W plane ignores the trailer, which is why it rides only after one (the 1.3.2 parser reads such a frame byte-for-byte as before).
- **Sender**: wisp(s) only. In Off (paint disabled), and in Osc mode while the stream is stale, the wisp packs zero entries, so every claimed lamp finds its MAC absent and eases home. While painting, `WispRoster::snapshotStateForBroadcast` packs every claim whose `painted` flag `setLampPaint` has set, whatever the colour, so a lamp painted black paints black. A fresh claim with no colour assigned yet is omitted, so that lamp holds its own scene until its colour lands. No gossip relay (direct radio range only); it re-covers the whole claimed set on its own cadence.
- **Off / presence**: presence holds while STATE from the display wisp keeps naming this lamp. A fresh STATE that drops the lamp eases it home now; total STATE silence ages presence out after `kWispStateFreshMs` (60 s) as a failsafe. A paint-mode edge emits STATE out of cadence, on the next free loop pass, so on/off lands within a frame or two of the change.
- **Cadence**: every presence tick (~2 s), at a uniformly random offset after the HELLO, drawn fresh each tick (`stateTickOffsetMs` over `kStateOffsetMinMs`..`kStateOffsetMaxMs`, 200 to 800 ms, in `presence_beacon.hpp`), so a receiver's periodic deaf window cannot phase-lock against a fixed send time. `PresenceBeacon::emit()` schedules it in a `TickStateSchedule` that holds one pending STATE: a STATE still unsent when the next HELLO fires is replaced by that tick's. No resend ring: at up to 1470 B it overflows the claim-sized resend slot. Edge coverage instead comes from a burst window (`kStateBurstMs` ≈ 2 s, `kStateBurstIntervalMs` ≈ 700 ms in `presence_beacon.hpp`): a paint-mode edge re-emits STATE a few times over ~2 s so a take/release lost to coex is caught without waiting the full 2 s re-cover, which remains the backstop.
- **One fat frame per loop pass**: every STATE (paint-edge, burst copy and steady tick) waits in `PresenceBeacon::pump()` (`nextStateSend`) for a loop pass that sent no other fat frame: no HELLO, no CLAIM, no resend copy, and no `StatusEmitter::pump()` emit (wispStatus with its `MSG_WISP_PALETTE`, or wispConfig; `pump()` returns whether it ran one of those emits, and `loop()` passes that in). At most one STATE goes out per pass, the edge first, then a due burst copy, then the steady tick STATE, which waits for the next free pass when one of the others takes this one.
- **Per-frame globals**: `brightness` (space brightness), `driftRateMs` (drift interval, matches `WispConfig::driftIntervalMs`), `presenceFlags` (the same bitfield as this tick's `MSG_WISP_HELLO` flags, incl `WISP_HELLO_FLAG_PAINT_MODE`).
- **Encoding**: raw R, G, B per surface (base, shade) in each entry; W rides the W plane after the entries. `buildWispState` appends the plane when given a W buffer (the wisp always passes one when it packs entries). `parseWispState` sets `ParsedWispState::w` only when the frame is long enough for the whole plane, else `nullptr`, and the lamp reads W = 0 (`fillPendingWispState` / `wispStateColorsFor` in `pending_slots.hpp`). A parser that reads only `count*12` entry bytes ignores the plane, so the trailer needs no protocol version bump.
- **Drift fade trailer**: `WispRoster::snapshotStateForBroadcast` packs a record for each claim mid-fade (target = the stored drift colours, time left from `fadeMs`), in the same lock and entry order as the entries, and `buildStateFrame` appends it with `appendWispStateDriftFade`. Each frame takes one of three forms (`wispStateDriftFadeRecordsToSend`): **full**, a record for every fading entry, whenever they fit the frame (any count up to `WISP_STATE_DRIFT_FADE_MAX_RECORDS` = 57 with all fading; 57 entries all fading is 1451 B); **partial**, past that line, as many records as fit beside the PARTIAL mark, taking turns round-robin across frames from where the last frame stopped, so with all 100 claims fading each frame carries 4 records (1468 B) and every lamp's record comes round within 25 frames (about 50 s at the 2 s cadence); **none**, no trailer at all when nothing is fading, byte-identical to a frame without the feature.
- **Lamp drift fade**: `decodeOwnWispDriftFade` looks up the lamp's own record (`lookupWispDriftFade`) and checks the trailer's form (`walkWispDriftFade`) on the recv task before the slot copy, so only copies run under portMUX, and `Compositor::applyWispStateSlot` feeds each surface: with its record, `LayerStack::syncWispFade` fades the wisp layer to the target over the time left on `lamp::fade`'s curve, anchored at the lamp's own `now` (no shared clock). A record for a fade already heading to that target, ending within `kDriftRetimeToleranceMs` (1 s) of what it says, changes nothing, so repeats never restart it; otherwise the fade starts (or retimes) from the colour the layer shows, or from the plain colour while the layer is hidden, as when a lamp joins mid-fade. A partial frame without its record leaves a running fade be and otherwise eases to the plain colour. A full frame without its record, or a frame with no trailer, eases to the plain colour as before, ending any fade, which is how Manual, Off, palette snaps and claim changes reach the lamp. A malformed trailer reads as no record and the STATE still applies. A fade carries over only between frames of one unbroken paint from one wisp: after the lamp was dropped from STATE, went without a fresh STATE for `kWispStateFreshMs` (60 s), or its display wisp changed, a partial frame without its record takes the plain colour. `drainWispState` notifies the app when the colours the lamp is heading to change (`wispStateHeadingBaseColor` / `wispStateHeadingShadeColor`), once per drift step on a lamp with records, and `CHAR_WISP_STATUS` reports those colours. Lamps older than the trailer read the plain colours and step every frame, as below.
- **Full-set frame**: one v2 frame carries the whole painted set; no windowing. `WISP_STATE_MAX_ENTRIES` (103) is derived as the most entries plus W plane that fit `ESPNOW_V2_FRAME_MAX` (1470), which keeps it above the wisp's claim cap (`WISP_ROSTER_MAX_LAMPS` = 100). Past the cap the extras truncate cleanly.
- **Lamp-side cache**: each lamp accumulates per-lamp `{base, shade, lastSeenMs}` entries in `WispFleetCache` (capacity 100) from STATE entries (`LampRoster::cacheWispState` takes the drained STATE slot; base and shade are RGBW, W from the W plane, W = 0 when the frame has no plane), upserting per MAC with per-entry staleness eviction on the 60 s claim window. The cache holds the colours the wisp assigns, so the app's chips show where each lamp is going: an entry with a drift fade record caches the record's target (`fillPendingWispState` copies each other lamp's target over its entry and marks it in `PendingWispState::targeted`; the lamp's own entry keeps the frame colour for its render and caches its own record), every other entry its frame colour. A partial frame keeps the colours already cached for an entry it carries no record for, since that entry's frame colour is a fade's in-between; an entry not cached yet takes the frame colour. The partial frame does not say which of those entries are fading, so the keep holds for all of them. A lamp starting a new step keeps its previous target until its record comes round, and a fade shorter than its round-robin turn gets no record at all, so the chip can hold the step-before colour for one or more steps; one first cached from a partial frame keeps that frame's in-between the same way. Frames go partial once the fading records stop fitting beside the entries (`wispStateDriftFadeRecordsToSend`): 5 fading of 100 entries, 30 of 80. A shuffle, palette change, Manual colour or source switch ends every fade, so its frame has no records and every chip takes the new colours from it. Lamps older than the trailer cache the frame colours, in-between included. `MSG_WISP_CLAIM` entries accumulate the same way. The union of both fresh sets feeds the `CHAR_WISP_CLAIMS` blob (see below) so a lamp painted before its claim message arrives is not invisible.

### Tier 2: Wisp control

**`MSG_CONTROL_OP` (0x03)**, wisp control envelope. Unicast or broadcast.
```
header(6) + targetMac(6) + sourceMac(6) + payloadLen(2 LE) + payload(N)
```
`payload` is opaque to the relaying lamp: a `wispOp` exactly as the app wrote it to `CHAR_WISP_OP`, sealed or plaintext (see the wispOp framing below), or the wisp's plaintext `wispStatus` / `wispConfig` JSON. Each JSON payload carries a `char` tag. Lamps on older firmware also sent lamp settings here (`brightness`, `shadeColors`, `baseColors`, `expressionOp`, `knockout`).

CONTROL_OP does not carry `triggerExpression`; directed expression triggers ride MSG_COMMAND.

Only wisp traffic uses CONTROL_OP between devices: a lamp unicasts the app's `wispOp` to its display wisp, and the wisp broadcasts `wispStatus` and `wispConfig`. A lamp never sends lamp settings to another lamp, and the app never routes them through one. A lamp still parses, dedups and relays every CONTROL_OP whatever its tag, so lamps of any version coexist, but from a mesh-received op it takes only `wispStatus` and `wispConfig` (`inboundControlOpKind`, `applyInboundControlOp`); any other tag (an older lamp's settings, a relayed `wispOp`) is relayed and dropped. The lamp-setting tags apply only to the app's own `CHAR_REMOTE_OP` write on the lamp it is connected to.

The unacked broadcast types a lamp sends (`MSG_COMMAND`, `MSG_COLOR_QUERY`, `MSG_COLOR_INFO`) have no per-frame retry, so each send buffers the identical frame (same seq) in a per-type `ResendRing` and `MeshLink::tick()` re-broadcasts it `kResends` more times, `kResendGapMs` (40 ms) apart — spaced so the copies fall in different RX-scan gaps rather than one hole. The gap must exceed the ~15 ms scan window, which only holds because the lamp runs a uniform continuous 1.5% BLE scan with no periodic high-duty burst to black out RX. The rings are per-type (not one shared ring) so a command fan-out's replays don't crowd out a colour query's; a lamp's only control op, the unicast wispOp, has its own ring (`controlOpUnicastResend_`, below); a command's ring holds one slot per fan-out target so every peer's frame stays in flight, and a command frame with a payload larger than the ring's 358 B budget sends once; the colour-query ring holds `kColorQueryResendSlots` (3) slots so the Lioness's three lions can query at once, each keeping its resends. A caller that may send more within the resend window (`kResends` × `kResendGapMs`) waits on `MeshLink::colorQueryResendFree()` (`ResendRing::idle()`: the slot the next enqueue takes has no copies left), and a lamp answers queries only while `colorInfoResendFree()`, so no reply's resends are cut short. LAMP_DEBUG logs `[resend.overwrite] buf=… slots=… lost=…` when an enqueue does cut one; the colour-query ring is `buf=18 slots=3`, and on the 1-slot control-op ring a replace is by design. `MSG_COMMAND` is how a cascade reaches each nearby lamp, so this is what makes a triggered-expression wave survive coex loss. The receiver's per-type `DedupRing` collapses the copies to one apply; receive-side state, no wire change.

**Wisp envelopes** (plaintext JSON, broadcast):

`wispStatus`, wisp → fleet, periodic state report.

Off mode (source == "off") — carries `offColor`; the settings ride `wispConfig` (below) in every mode:
```json
{
  "char":"wispStatus",
  "source": "off",
  "wifiConnected": true,
  "sourceLive": false,
  "lastSeenMs": 14823,
  "configSplit": true,
  "hasPassword": true,
  "manualId": "",
  "offColor": "ffb43c00",
  "name": "living room"
}
```

Manual/Osc mode — no `offColor`; `oscRole` rides in any mode off its default:
```json
{
  "char":"wispStatus",
  "source": "osc",
  "wifiConnected": true,
  "sourceLive": true,
  "lastSeenMs": 14823,
  "configSplit": true,
  "manualId": "59a8ae37",
  "manualSeq": 4321,
  "swatchesSeq": 812,
  "oscRole": "secondary",
  "paletteIdPrefix": "abc12345",
  "name": "living room"
}
```
- **Sender**: wisp(s) only. Lamps gossip-relay (the `MSG_CONTROL_OP` relay rule) but never originate. The wisp's shared seq counter starts at a random value each boot (see Sequence numbers and dedup).
- **Cadence**: 30 s heartbeat plus two kinds of trigger, decided by `StatusCadence` (`test_status_cadence`). Every emit is coalesced to at most one per 5 s (a due emit inside the window is deferred, never dropped). An applied op opens a ~20 s burst that re-broadcasts the status every 2 s, so at least one copy clears a multi-second coex reception blackout on the lamps and the app's control-op confirmation survives; another op inside the burst restarts its 20 s. Burst triggers (`triggerOnChange()`): every applied wispOp (`setSource`, `setManualPalette`, `setOscRole`, `setOsc`, `setWifi`, `wifiReconnect`, `setOffColor`, `shuffle`, `setDrift`, `setName`, `setPassword`, `setLedStrip`, `setBrightness`, `setSwatches`) and the serial console's `src:`, `osc:role`, `osc:mode`, `osc:slot`, `osc:addr` and `paint:swatches` commands. Single-emit triggers (`requestEmit()`, no burst, and one inside a running burst neither extends nor shortens it): `pollStatus`, a WiFi connect/disconnect or Ethernet up/down edge, the WiFi channel-mismatch flag setting or clearing, a flip of the HELLO `wifiConnected` / `sourceLive` flags, and the OSC stream going stale (or blank) and resuming. One WiFi edge can give two emits 5 s apart, since the connectivity check and the HELLO flag flip each request one; a flapping AP costs at most one emit per 5 s. `MSG_WISP_PALETTE` is emitted in the same tick (see Tier 1) so the app's view of the palette converges on the same cadence. A status is held back while a `wispConfig` went out less than 250 ms ago (see `wispConfig` below).
- **Fields: live state only.** The status carries the wisp's live state: `char`, `source`, `wifiConnected`, `sourceLive`, `lastSeenMs`, `configSplit`, `hasPassword`, `manualId`, `manualSeq`, `swatchesSeq`, `offColor`, `oscRole`, `paletteIdPrefix`, `name`, `ethIp`, `wifiChannelMismatch`, `wifiApChannel`. The wisp's settings (`shuffleSeed`, `opSeq`, `driftIntervalMs`, `driftFadePct`, `ledType`, `px`, `brightness`, `swatches`) and its OSC send-to address (`ip`) ride only `wispConfig`, which keeps them off the 30 s heartbeat every lamp relays. `"configSplit": true` says so on every status. The app takes the settings only from `wispConfig` (`WispStatus.withConfig`), never from a status, and takes a status without the marker (a wisp on older firmware, or the lamp's HELLO-only merge) as one the wisp did not send (`WispStatus.fromWisp`). Who loses what: through a lamp older than 1.2.8, which caches no `wispConfig` and serves no `wispconfig` section, the settings never reach an app, so a password change there is refused (no `opSeq` baseline); an app older than 1.2.8 does not know the marker, shows the settings at its parser defaults and writes them back on a save, and reports a password change failed though the wisp applied it; an app from 1.2.8 that predates the refill below can sit on its loading line until the wisp's settings next change, and can confirm a wrong password from a stale held `opSeq`. So every phone that opens a wisp needs a current app. While a split status's wisp has no config held, the app re-sends `pollConfig` (through its rate limit) and re-reads the `wispconfig` section on a backoff from 1 s to 30 s, restarted at 1 s on each reconnect, since a lamp that booted after the wisp or cleared its cache on a display switch holds none, and no notify follows a config the lamp already had. Until a read has shown the lamp serves the sections (every build read can land before the auth handshake, and a lamp holding no config merges no `configLastSeenMs`), each backoff step re-reads the status section instead, which marks them on a lamp that has them. Its settings forms show a loading line meanwhile, or, through a lamp older than 1.2.8 (which serves no `wispconfig`), ask for that lamp to be updated. The painted-lamps preview predicts nothing until the settings, `shuffleSeed` among them, are known. A password change through a split status needs a fresh `wispconfig` read for its `opSeq` baseline and is refused without one, and its confirm waits up to 10 s, since `opSeq` then arrives only through a config read.
- **Payload budget — degrade by construction**: guaranteed ≤ 576 B (`CONTROL_MAX_PAYLOAD`). A guaranteed core — `char`, `source`, `wifiConnected`, `sourceLive`, `lastSeenMs`, `configSplit`, plus `hasPassword` when true, `manualId`, and `manualSeq` and `swatchesSeq` when not 0 — is pinned by a native test at 208 B at worst-case field widths (a 16-digit `lastSeenMs`, an 8-character `manualId`, a 5-digit `manualSeq` and `swatchesSeq`), so the builder always produces a frame and no cap sheds `configSplit`, `manualId`, `manualSeq` or `swatchesSeq`. Every other field is add-if-fits in priority order: `offColor` (Off only), `oscRole`, `paletteIdPrefix`, `name`, `ethIp`, `wifiChannelMismatch`, `wifiApChannel`. `offColor`, `oscRole` and `paletteIdPrefix` lead: a dropped `offColor` silently renders the app's amber default, a dropped `oscRole` shows the wrong role selected, and an app that predates `manualId` re-reads the palette on a changed prefix. The pathological worst case (380 B — Off mode, every field widest, both mismatch fields, a 15-character `ethIp`; 400 B if the 20-byte name is all `"`, each escaped to 2; 361 B in Manual; ArduinoJson escapes `"`, `\` and `\b \f \n \r \t` to two bytes and passes other control bytes through raw; `test_status_json`'s `test_worst_case_untruncated_length`) fits the cap whole, so nothing sheds on the mesh; the order governs only if the frame grows.
- **The 512 B characteristic.** The 576 B cap is the mesh frame's, and it is not the binding ceiling for a direct read: `CHAR_WISP_STATUS` is a single characteristic value that NimBLE caps at 512 B (`BLE_ATT_ATTR_MAX_LEN` in the vendored `ble_att.h`, which overrides a build flag; see the page-protocol comment in `ble_control.cpp`), and past it `setValue` stores a zero-length value that blanks an app's whole wisp view. The lamp's merge adds its own fields (`wispMac`, `wispVersion`, `helloFlags`, `helloPaletteIdPrefix`, `helloLastSeenMs`, `statusLastSeenMs`, `configLastSeenMs`, `controllingBase` / `controllingShade` and the wisp colours), up to 301 B, so the status is not guaranteed to fit: the widest status, 380 B, merges to 681 B. The app therefore reads the status through the `wispstatus` page section, which has no ceiling. For older apps the direct read sheds `helloPaletteIdPrefix`, `helloLastSeenMs`, `statusLastSeenMs` and `helloFlags`, in that order (`kShedOrder`), until the value fits, and so does every notify, since `notifyWispStatus` serves the same `kWispStatusCharMaxLen` merge. The app acts on none of these but `statusLastSeenMs`, which only tells it whether a status is fresher than its held `wispConfig` (the OSC send-to address, `ip` below); shed, the status counts as fresher. That brings a typical status well under 512 B; the widest still merges to 571 B with all four shed (591 B when its 20-byte name is all `"`), and a status that still does not fit is served as before: its notify goes blank and the app re-reads the `wispstatus` section. `configLastSeenMs` never sheds, and `configSplit`, `manualId`, `manualSeq` and `swatchesSeq`, part of the wisp's payload, are never in the shed order.
- **Omit-when-default**: a field whose value equals the app parser's missing-field default is left off the wire — `hasPassword` false, `wifiChannelMismatch` false, `wifiApChannel` 0, `manualSeq` 0, `swatchesSeq` 0, `oscRole` "primary", empty `name` / `paletteIdPrefix` / `ethIp`. `sourceLive`, `configSplit` and `manualId` are always sent, so an absent key reads as an older wisp.
- **`source`**: `"off"` | `"manual"` | `"osc"`. Consumed by the Flutter app to surface and round-trip the source-toggle state. A wisp that stored the retired Aurora mode boots as `"off"`; an app reading `"aurora"` from an older wisp maps it to off.
- **`sourceLive`**: `true` while `source == "osc"` and a non-blank palette has arrived on the OSC target's address (see `setOsc`); for Straylight, also something from its feed (that palette or any other `/straylight/` message) within the last 30 s, while a Maestro palette never goes stale. The same signal as HELLO flag bit 2. The app shows "Waiting for Straylight", or "Waiting for the Maestro" when `oscMode` is `"maestro"`, while it is false in Osc mode.
- **`oscRole`**: `"primary"` | `"secondary"` | `"tertiary"` | `"fill"`, the Straylight palette the wisp follows. Present in every source mode when the role is not `"primary"` (the app default), so the app shows the stored role the moment Straylight is picked.
- **`offColor`**: packed lowercase-hex `"rrggbbww"` (8 chars, no `#`), the ring color used in Off mode (W = warm white). Present only when `source == "off"`. The app defaults to warm amber when absent.
- **`manualId`**: the wisp's stored Manual palette, in every source mode: `""` when it is empty, else its `manualPaletteId` (`WispConfig::manualPaletteStatus`, `statusManualId` in `palette_id.hpp`; the app computes the same value with `WispRepository.statusManualId`). It rides the guaranteed core, so a status without it is from a wisp that predates it or is the lamp's HELLO-only merge, never a shed field or an empty palette. The app (`WispNotifier`) takes a status without it as leaving the palette unknown, whatever its `paletteIdPrefix`, so on a wisp whose firmware predates it the editor shows its loading line and Save sends nothing. Keyed by the `wispMac` that stated it, the app reads the `wisppalette` section on a status from that wisp while the palette is unknown, and marks the palette known, empty included, only when a read succeeds (`WispRepository.readManualPalette` returns null for a failed read), the last status heard is still from that wisp, and the read's id equals the id that wisp stated last when the read lands. A read of another palette (a lamp cache that lags, a late older status) leaves the palette unknown, and the next status reads again. A status stating an id other than the saved palette's, or stating one from a wisp the held palette did not come from, returns the palette to unknown as it lands, even when the source-write guard drops it (the editor redraws into its loading line then too) or another read holds the link; the read then waits for the next status the guard lets through while the link is free. A confirmed save marks the palette known only while the last id that wisp stated is the one the save sent; a status stating another between the echo and the write's ack leaves it unknown, and so does any status from another wisp heard last before the ack. A status the wisp did not send (the lamp's HELLO-only merge, which has no `source`: the lamp just booted or adopted a new display wisp, so its palette cache may be empty or another wisp's) returns the palette to unknown and starts no read. No read started for such a status counts, whatever lands while it is in flight, and no read and no save's confirm marks the palette known unless the latest status heard is one that wisp sent (`WispNotifier._heardInFull`), so the editor shows its loading line until the wisp's next status. A present status from a wisp other than the one the known palette came from returns the palette to unknown (a display switch). So does a reconnect, which also forgets every stated id until the wisp states it again, since another phone may have changed the palette during the drop; a read in flight across it does not count. The editor shows its loading line meanwhile, up to the wisp's next status (the 30 s heartbeat when it is idle). While the palette is unknown, whatever made it so, a save (`WispNotifier.setManualPalette`) sends nothing, and a save in flight sends no further copy once it has gone unknown, even when a read has made it known again by the next copy, since that read may be another wisp's palette; a palette sheet left open across any of these disables its Save under the loading line until the palette is known, without closing (`ColorStopsSheet.saveUnavailable`). Residual: a late older `""` met by a read served before the auth handshake, which reads empty, shows the palette empty until the next status. The saved palette changes on a `wisppalette` read that marks the palette known, an empty one included, or on the user's own confirmed save (`WispNotifier._applyPaletteConfirm`). `WispNotifier` is not rebuilt on reconnect, because `LampShell` watches it and stays mounted through one, so on the next connect it subscribes to the status notify again (`_subscribeStatus`): the lamp is unbonded and its subscription dies with the link. That subscribe runs on the connected edge, before `FbpBleClient.connect` returns, so `FbpBleClient` drops its cached GATT services on every disconnect event, not only in `connect` and `disconnect`; otherwise the subscribe would resolve the old link's characteristics. The saved palette and the editor draft both live in `manualPaletteDraftProvider`, keyed by the relay lamp and kept alive past the notifier, so a notifier built on a later visit to the lamp can tell an untouched draft from an edit: it clears an untouched draft and its saved palette, so the visit's own read seeds the editor as on a first visit (a palette changed or emptied elsewhere shows as the wisp holds it), and keeps an edited one, which stays an unsaved edit.
- **`manualSeq`**: the `seq` of the last `setManualPalette` the wisp applied since boot, when that op carried one; omitted at 0 (no `seq` on that op, or none since boot). Set where the palette is stored and RAM-only, so a reboot clears it; an applied palette op without a valid `seq` clears it, and one rejected for a missing `colors` leaves it (`WispConfig::setManualPalette`, `wisp_op_dispatcher.cpp`). Compared for equality only, never order. `WispNotifier.setManualPalette` sends every save with a `seq` and confirms it on the first status from that `wispMac` whose `manualSeq` equals it and whose `manualId` equals the id of the colours in the op sent (`WispRepository.sentManualId`), in any source mode, since the wisp stores the palette whatever the mode (`_confirmPaletteEcho`). An echo heard before the save's write call reports an error still confirms it, since a lost response does not mean a lost op; the same holds for every op `WispNotifier._sendConfirmed` sends. A status from before the save, a late older one, or one from a wisp that rebooted after storing it carries another `manualSeq` and confirms nothing; a save another phone made with the same `seq` confirms only when its palette is the same. The notifier picks its first `seq` at random in 1..65535 (`WispNotifier.debugSeqStart` is the test seam), steps it by one per save, wrapping past 0, and skips the `manualSeq` that wisp echoed last; every resend of one save reuses its `seq`. No status read precedes the send.
- **`swatchesSeq`**: the `seq` of the last `setSwatches` the wisp applied since boot, when that op carried one; omitted at 0 (no `seq` on that op, the console's `paint:swatches`, or none since boot). Set with the style and RAM-only, so a reboot clears it; an applied style op without a valid `seq` clears it, and one rejected for a missing or non-bool `swatches` leaves it (`WispConfig::setPaletteStyle`, `wisp_op_dispatcher.cpp`). Compared for equality only, never order. Every applied `setSwatches` sets it, the same value as the held style included, so after picks A then B a status carrying B's `seq` says B was the last pick applied, and a late copy of A shows A's. The style itself rides only `wispConfig` (`swatches`).
- **`paletteIdPrefix`**: first 8 chars of the live palette id. In Manual mode the id is an 8-char FNV-1a hash over the palette's canonical wire bytes (r,g,b per color, plus w only when w != 0), the same hash `manualId` carries. The wisp clears the id (`CurrentPalette::clear`), so the status omits the prefix, in these cases: on the transition to Off; on entering Manual with an empty stored palette; on a `setManualPalette` with an empty `colors` list applied in Manual; and in Osc from the transition until the first non-blank palette, and again whenever a blank palette or a stale stream holds the lamps at Off (`WispController::holdOscStream`). The app reads nothing from it: the Manual palette's state comes from `manualId` alone.
- **`name`**: wisp display name, ≤ 20 characters.
- **`hasPassword`**: `true` when the wisp has a control password set; omitted when false (the app default).
- **`lastSeenMs`**: milliseconds since the wisp booted, read at emission from a 64-bit clock (`wisp::uptimeMs`), so it grows for as long as the wisp stays up and restarts from zero only when the wisp reboots. Its widest value, at the top of `esp_timer_get_time`'s range, is 16 digits; the size figures above use that width. A lamp serving the cached status passes it through unchanged (`mergeWispStatusJson` adds its own `helloLastSeenMs` / `statusLastSeenMs` beside it), so a re-served copy carries the stamp of the emission it caches. The app does not compare it.
- **`wifiChannelMismatch`** / **`wifiApChannel`**: set when the wisp's channel-6 STA guard (see below) dropped an association to an AP on the wrong channel. `wifiChannelMismatch` true explains a `wifiConnected` false the app would otherwise blame on bad creds; `wifiApChannel` is the offending channel. Both omitted in the normal case. Recovery is a `wifiReconnect` or fresh `setWifi` op, switching the source away from Straylight and back, or Ethernet going down while the source is Straylight, any of which clears the flag and re-emits.
- **`ethIp`**: the wisp's wired Ethernet address, present only while the W5500 has a link and a DHCP lease (absent on a wisp with none fitted). It explains a `wifiConnected` false in Osc mode, since the STA stays down while Ethernet is up, and it is the address to point Straylight's OSC feed at. Its up/down edge re-emits the status like a WiFi connect edge. A `wifiChannelMismatch` held from before Ethernet came up stays set (only the join becoming wanted again clears it), so while `ethIp` is present the app treats it as stale and shows the Ethernet line instead.
- `manualPalette` is intentionally NOT carried here, it ships via the separate `MSG_WISP_PALETTE` broadcast.
- **Lamp-side cache**: each lamp keeps the latest `wispStatus` for its display-slot wisp in `LampRoster`. `CHAR_WISP_STATUS` reads and the `wispstatus` page section serve the same merge (`mergeWispStatusJson` in `wisp_status_merge.cpp`) of this cache with the last `MSG_WISP_HELLO` snapshot, the cache's stamps and the lamp's own wisp-control state; the manual palette is served on its own `wisppalette` section. `statusLastSeenMs` is the lamp's own `millis()` when it cached the status (`LampRoster::cacheWispStatus`), served unchanged, so a re-served copy carries the same value, each newly cached status a larger one, and a wisp reboot leaves it alone. Adopting a wisp (`LampRoster::adoptWispLocked`) resets it to 0, and the merge omits it until a status from that wisp is cached. It restarts when the lamp reboots and wraps with the lamp's `millis()` at about 49.7 days of uptime.

`wispConfig`, wisp → fleet, the wisp's settings.

```json
{
  "char":"wispConfig",
  "ledType": "GRBW",
  "px": 60,
  "brightness": 80,
  "driftIntervalMs": 90000,
  "driftFadePct": 40,
  "shuffleSeed": 7,
  "opSeq": 3,
  "ip": "192.168.1.42",
  "swatches": false,
  "oscMode": "maestro",
  "oscSlot": 3,
  "oscAddr": "/lamp/palette"
}
```
- **Fields**: `ledType`, `px`, `brightness`, `driftIntervalMs`, `driftFadePct`, `shuffleSeed`, `opSeq`, `ip`, `swatches`, `oscMode`, `oscSlot`, `oscAddr`; the drift fields, `opSeq` and `ip` are described below. `ledType`, `px` and `brightness` are the LED strip and brightness settings, `shuffleSeed` is the shuffle seed, `swatches` is set by `setSwatches`, and `oscMode` (`"straylight"` | `"maestro"` | `"custom"`), `oscSlot` (1..10) and `oscAddr` (the Custom address, `""` when none is stored, held whatever the sub-mode) by `setOsc`. Every field rides every time, defaults included, so a received `wispConfig` is complete and an absent key never stands for a default. Worst case 255 B (`test_config_worst_case_pinned`, every field at its type's widest, `oscMode` `"straylight"`, a 15-byte `oscAddr`), which is the ceiling: the wisp's builder refuses 256 B and the lamp's ingest slot (`kPendingWispConfig`) drops anything past 256 B. No key fits beside it: a new key needs room taken from another, or a larger lamp slot. A Custom address never needs a JSON escape (`test_config_fits_with_every_custom_address_byte`), so the 15-byte cap holds the pin. `opSeq` is not a setting, but it belongs here because it moves only when the config does (a sealed op), and the app's password flow confirms on it.
- **`driftIntervalMs`** / **`driftFadePct`**: the drift cadence, and how long each drift step fades as a percentage of it (see `setDrift`). They apply in every source mode, and the app's drift form shows in every mode.
- **`ip`**: where an OSC sender reaches the wisp on UDP 9000: the Ethernet lease while Ethernet is up, else the STA address while the WiFi join holds, else `""`. Never the softAP address (the pre-mesh lamps' network). An IP change from a WiFi or Ethernet edge rides that edge's status emit; the changed config follows it, and the status emits of that change's ~20 s config window repeat it (see Cadence). A WiFi edge sends the config at least twice, since its HELLO flag flip requests a second status; an Ethernet edge with no STA join sends one status and one config. An address change with no connectivity edge shows after the next status, at worst the 30 s heartbeat. The app shows where to send under the OSC source (`WispStatus.oscSendTo`): the status `ethIp` while the wisp is on Ethernet, since the wisp always picks it first, else `ip`, so a wisp that predates `ip` still shows its Ethernet address. When the config the app holds reached the lamp after the status (the `configLastSeenMs` the app read it under, `WispStatus.heldConfigSeenMs`, past the status's `statusLastSeenMs`; the lamp stamps a config only when it changes), the config is the fresher report and `ip` shows instead, which covers an Ethernet drop whose one status was lost. Comparing against the held config, not the lamp's newest stamp, keeps the Ethernet address up while a config that landed after the status is still being read. While the OSC panel is open the app sends `pollConfig` (through its rate limit) for each new status from the wisp, cached no earlier than the held config, whose link state contradicts the held `ip` (`WispStatus.ipDisagreesWithLink`: an `ethIp` other than `ip`, `wifiConnected` with an empty `ip`, or neither with one set), so a config frame lost after a link edge is asked for again. One edge goes unseen: from Ethernet back to Wi-Fi with that config lost, the old Ethernet address shows until the next config arrives.
- **`opSeq`**: monotonic counter the wisp bumps each time it accepts and applies a *sealed* wispOp (plaintext ops don't move it). Sealed ops carry no direct ACK, so the app confirms one landed by watching this advance — the password-change flow persists the new secret only after `opSeq` steps past the value it read before sending. RAM-only: resets to 0 on wisp reboot, so the app treats only a strict increase as confirmation.
- **Envelope and relay**: the same plaintext `MSG_CONTROL_OP` broadcast as `wispStatus`, gossip-relayed by every lamp under the same rule. It is an additive JSON tag inside an opaque payload, so no protocol bump: a lamp that predates it relays it unchanged and drops it at apply (its control-op apply had no branch for it), so an app connected through such a lamp gets no settings (see the `wispStatus` fields).
- **Cadence**: sent at boot, once per `pollConfig` (coalesced: at most one per 5 s, a poll inside the window deferred, never dropped), and after any status emit that finds the config changed, then again after every status emit for the rest of that change's ~20 s burst. The repeats ride the status emits, so they come every 2 s only while an op's status burst runs. "Changed" is a fingerprint of the serialized config taken at each status emit, so any sealed op re-sends it, `setSource` and `setName` included, because its `opSeq` bump changes the config; a plaintext op that changes no setting does not. Never within 250 ms of a status in either order (`ConfigCadence`, `test_config_cadence`): a lamp that predates `wispConfig` holds one inbound control op per loop pass, so of two back-to-back frames the first would be lost. Current lamps route both broadcasts to their own slots (`peekWispBroadcast`), and the wisp acts only on a control op addressed to its own MAC (`controlOpForWisp`), so no broadcast, its own relayed back or a peer wisp's, ever overwrites a pending app op in its single op slot. It does not ride the 30 s heartbeat.
- **Lamp-side cache**: each lamp caches the display-slot wisp's latest `wispConfig` beside its `wispStatus`, under the same admission and stickiness, and clears both when a rival takes the slot. A payload whose bytes differ from the cached one notifies `CHAR_WISP_STATUS` and stamps `configLastSeenMs` into the merged status; an identical re-send through a burst does neither. The app re-reads the `wispconfig` page section when that stamp moves (a read skipped while another is in flight runs as soon as the link is free), and merges it over every status from the same wisp. The section serves the cached payload verbatim, `"{}"` until one arrives. A `setDrift`, `setBrightness` or `setLedStrip` write shows in the app at once, and a write the wisp never applies brings no new config, so the app reads the section back from 5 s after the latest such write (`WispNotifier._readBackAfterWrite`, through the config refill, which also polls). A read-back that fails, or is skipped while another read holds the link, is retried on the refill's backoff until one lands; a write during a read-back gets its own; a reconnect restarts it at 1 s. A read-back that lands before the lamp holds the wisp's new config shows the old value until that config arrives and its stamp moves.

`wispOp`, app → wisp, control writes proxied through the paired lamp. The lamp unicasts the op as `MSG_CONTROL_OP` to its display-slot wisp's MAC (single-hop scope: the wisp acts only on ops whose target is its own MAC, never a sibling's or broadcast). The C6 wisp's bursty RX-scan can drop every 802.11 MAC-ARQ attempt inside one scan gap, so this path arms its own `controlOpUnicastResend_` ring: `MeshLink::tick()` re-sends `kResends` more copies `kResendGapMs` apart, each copy also unicast (extracting the target MAC from the frame at `HEADER_SIZE`, individually MAC-acked) and collapsed by the wisp's dedup. With no display wisp in range the op is dropped rather than broadcast.

**Wire framing.** The payload written to `CHAR_WISP_OP` (and carried verbatim inside `MSG_CONTROL_OP`) is in one of three shapes:
- `0x02` prefix: AES-GCM sealed. `[0x02][12B nonce][16B tag][ciphertext]`. Used when the wisp has a password set. Key derivation: HKDF-SHA256, salt = `uuidSaltLE16(CHAR_WISP_OP)`, info = `"lamp-v1"\0wispOp`, IKM = wisp password. Same framing as lamp control-op sealing.
- `0x01` prefix: explicit plaintext marker. `[0x01][JSON]`. Accepted when no password is set.
- Bare `{`: plaintext JSON at offset 0. Accepted when no password is set.

When a password is set, the wisp rejects plaintext (both `0x01`-prefixed and bare) with three exceptions, all always accepted plaintext regardless of password state:
- `setManualPalette` — an **integrity exception**: palette colors are unauthenticated by design, because an attacker in BLE proximity can push override colors anyway; sealing adds nothing under the proximity threat model.
- `pollStatus` and `pollConfig` — **read-only**: they only trigger a re-broadcast of state every lamp already relays, so an app without the password can still refresh a password-protected wisp.

**Replay protection.** The wisp maintains a RAM-only bounded nonce ring (32 entries). A seen nonce is rejected; a forced reboot resets the ring. Config ops are low-value and idempotent, so reboot-replay is an accepted ceiling.

```json
{"char":"wispOp","op":"setSource","mode":"osc"}
{"char":"wispOp","op":"setOscRole","role":"secondary"}
{"char":"wispOp","op":"setOsc","mode":"maestro","slot":3}
{"char":"wispOp","op":"setOsc","mode":"custom","address":"/lamp/palette"}
{"char":"wispOp","op":"setWifi","ssid":"...","pw":"..."}
{"char":"wispOp","op":"setDrift","intervalMs":120000,"fadePct":50}
{"char":"wispOp","op":"setName","name":"living room"}
{"char":"wispOp","op":"setPassword","password":"newpass"}
{"char":"wispOp","op":"setManualPalette","colors":[[255,0,0],[0,255,0]]}
{"char":"wispOp","op":"pollStatus"}
{"char":"wispOp","op":"pollConfig"}
```
- **Sender**: the Flutter app writes the payload (sealed or plaintext) to `CHAR_WISP_OP` on any paired lamp; the lamp unicasts it as `MSG_CONTROL_OP` to its display-slot wisp's MAC (dropped when no display wisp is in range).
- **Receiver**: the addressed wisp only. Lamps relay a `wispOp` and never apply it (`applyInboundControlOp` takes only `wispStatus` / `wispConfig`).
- **Wisp dedup**: the wisp runs its own 64-slot ring (`ControlOpInbox::dedup_`) keyed on `(sourceMac, msgType, seq)` so the unicast resend copies of the same op don't re-apply. A tuple ages out after `kDedupMaxAgeMs` like every other ring.
- **`setSource`**: `mode` is `"off"` | `"manual"` | `"osc"` (or numeric 0 | 1 | 3); anything else, `"aurora"` and 2 included, is `Malformed` and changes nothing. Persisted to NVS (key `srcMode`); a stored 2 or unknown value loads as Off. Selecting Manual or Osc turns paint mode on, which is the paint opt-in. Manual with an empty palette paints nothing: lamps ease home rather than keep the previous source's colours. In Osc the wisp listens for OSC 1.0 on USB serial (SLIP, sharing the console) and UDP port 9000 on every interface, bundles included, and paints from one address set by `setOsc`: in Straylight (the default) flat RGB floats 0..1 (1..50 colours) from `/straylight/palette/<role>/colours`, as below; in Maestro and Custom the address `setOsc` describes. Every interface means the softAP, the STA join, and wired Ethernet when a W5500 is fitted: the socket binds `INADDR_ANY`, and lwIP delivers a datagram from any netif to it. Once a palette is held, any parsed packet carrying a `/straylight/` address keeps it live, except one whose message for the followed role's own address is unreadable (it refreshes nothing); with nothing from the feed for 30 s (`OscFreshness::kStaleMs`, three of Straylight's 10 s UDP restates) the wisp holds lamps and its ring at Off (STATE packs no entries, ArtNet stops) with paint mode kept, and the next palette resumes painting with no app action. A palette message the decoder cannot read whole (a NaN or infinite float, an unknown type tag, more than 50 colours, a float count not divisible by 3) changes nothing. A blank palette (no channel above zero, which Straylight sends for a role with nothing bound) counts as no palette and drops to that hold at once. The ring follows every palette change; lamp re-assignment, the out-of-cadence STATE and ArtNet follow at most once a second, trailing edge included, so a fast-moving palette cannot flood the mesh. A role change keeps painting the old role's palette until the new role's first one lands.
- **OSC transport**: USB serial or wired Ethernet are the recommended paths. Ethernet (a W5500 on SPI, `net/eth_link.cpp`, wiring in the wisp README) takes the feed off the radio entirely, and the wisp blocks IPv4 multicast at the W5500 (the core's `ETH.begin` turns all-multicast on) so multicast sACN on a lighting LAN never costs the C6 an SPI read or a heap buffer. lwIP's 6-datagram socket queue below still applies over the cable. Broadcast is not filtered by the chip, so each broadcast frame on the cable (ARP, Art-Net broadcast, ArtPoll) costs an SPI read and a full-frame heap buffer in the W5500 receive task, above the loop task in priority; the wisp belongs on a segment without broadcast Art-Net. The framework ships with IP forwarding on (`CONFIG_LWIP_IP_FORWARD=y`), so the wisp routes between the softAP's 192.168.4.0/24 and the Ethernet netif with no NAT, the same exposure as the STA join; the wisp README has the details. Over WiFi UDP the wisp receives Straylight's whole feed (every param, level and palette, not only its role's palette), all of it airtime on the shared channel-6 radio. lwIP queues at most 6 datagrams per socket and the loop drains it once per pass, behind a 5 ms `delay()`; a restate burst arrives faster than that and overflows the queue, and the palettes, sent last, are what drop. That can happen on every restate, so a palette change lost that way is not repaired by the next restate either: the lamps hold the old palette until the palette changes again and that datagram lands. The feed keepalive above stops this from also reading as stale. SLIP frames on serial share the text console: a frame that goes 200 ms without a byte is dropped and the console is back on text.
- **`setOsc`**: `mode` is `"straylight"` | `"maestro"` | `"custom"`, required; `slot` is an integer 1..10, optional; `address` is a Custom address, optional. An absent or `null` `slot` or `address` keeps the stored one, so switching sub-mode never moves either, and an address sent with another sub-mode is stored for a later Custom. A Custom address is printable ASCII (0x21..0x7E), 1 to 15 bytes, starts with `/`, and has none of `"` `\` `#` `*` `,` `?` `[` `]` `{` `}` (`oscCustomAddressValid`; the cases are `software/wisp/test/test_osc_address/osc_address_cases.hpp`, which a client checking addresses before sending mirrors). Anything else, a missing `mode`, a slot out of range or not an integer, an address that is not a string, is `""`, carries a `\u0000` or breaks the rule, or `"custom"` with no address sent and none stored, is `Malformed` and changes nothing. Persisted to NVS (keys `oscMode` and `oscSlot`, u8, and `oscAddr`, string; an unknown mode loads as Straylight, a slot outside 1..10 as 1, an address the rule refuses as `""`, and Custom with no usable address as Straylight); reported back as `oscMode` / `oscSlot` / `oscAddr` in `wispConfig`. Gated like every config op: sealed once a password is set. Straylight is the `setSource` paragraph above, unchanged. Maestro paints from `/palette/live/<slot>`, matched exactly (`/palette/live/1` never takes `/palette/live/10`), and Custom from its stored address, matched exactly, both in either colour format a Limbic Maestro sends (its `colorFormat`), told apart by the type tags. Every argument `i` is Limbic hex, one `0xRRGGBB` per int (the top byte ignored). A string then only `f` / `i` is a Limbic float layout: the string names one channel per float, read as Straylight reads it (`am` and `uv` before single letters; `r` `g` `b` `w`, `a` amber, `u` UV; any other byte consumes its float and drives nothing; at most 16 channels), and the floats repeat in groups of the layout's width. Arguments that are all `f` or `i` but not all `i` read as RGB floats in threes, Straylight's own shape, for senders other than a Maestro. One channel rule on every format: r, g, b as sent; `w` drives the lamps' white LED; amber mixes into red at full and green at `kOscAmberGreen` (0.75, amber as #FFBF00); UV drops. Every channel clamps to 0..1 as read and again after mixing, and hex and RGB carry no white. A UV-only palette is blank. A message on that address that does not read whole (a NaN or infinite float, an unknown type tag, arguments that end early or run past the tags, a float count the group width does not divide, an empty layout or one over 16 channels, no colour, or more than 50 colours) changes nothing, and the wisp logs `[osc] refused <address> ,<tags>` at most once a second. A Maestro or Custom stream has no keepalive and never goes stale: lamps keep the last palette until the target or source changes. A blank palette holds lamps at Off at once, as in Straylight. In Osc, a `setOsc` that changes the sub-mode, the Maestro slot in Maestro or the address in Custom holds lamps and the ring at Off until the new address's first non-blank palette; one that leaves the target as it was (a resend), or one applied while the source is Off or Manual, changes no paint. An older wisp answers it as an unknown op (`Malformed`). The console sets the same with `osc:mode <straylight|maestro|custom>`, `osc:slot <1-10>` and `osc:addr </path>`. The app sends it from the Straylight | Maestro switch and the Maestro slot picker under the OSC source, shown only for a wisp whose `wispConfig` carries `oscMode` (`WispStatus.oscMode`); before that config is held the panel shows its loading line, and an older wisp gets the Straylight role picker and "Update this wisp to use Maestro." alone. A sender change carries no `slot`, so the wisp keeps its stored one, unless a slot pick is still confirming, which rides along; a slot pick sends `maestro` with it. Both confirm as `setSwatches` does (`WispNotifier.setOscMode`, `setMaestroSlot`), on `oscMode` and, for a slot, `oscSlot`; a pick stops resending once a status comes from another wisp, even one a pending `setSource` holds off, since the lamp relays every resend to the wisp it shows, and counts as unconfirmed. An `oscMode` the app does not know selects neither sender and asks for an app update. The app has no Custom control: a wisp reporting `oscMode` `custom` gets that same update-asking line.
- **`setOscRole`**: `role` is `"primary"` | `"secondary"` | `"tertiary"` | `"fill"`; anything else is `Malformed`. Persisted to NVS (key `oscRole`, u8, unknown loads as primary). Gated like every config op: sealed when a password is set. In Osc mode a role change keeps the stream live and lamps on the old role's palette until the new role's first palette lands.
- **`setWifi`**: persists credentials to NVS and restarts the STA join schedule (an attempt at once while the source is Osc). The relay lamp passes the payload through opaque; the wisp handles the WiFi join.
- **`wifiReconnect`**: restarts the STA join with the stored creds. The recovery path after the channel-6 guard drops an association; clears the mismatch guard. Read-only w.r.t. NVS.

**When the STA joins.** The STA join runs only while the source is Osc, the one mode that uses the LAN, and Ethernet is not up (`staWanted()` in `net/sta_join.hpp`: link plus a DHCP lease); in Off and Manual, or while Ethernet carries the feed, the wisp never scans or joins, and either condition arriving drops any association. Ethernet going down in Osc makes the join wanted again, which arms an attempt at once and clears a channel-guard halt the same way re-entering Osc does. Ethernet itself never touches the radio: the W5500 is its own MAC and PHY on SPI, so the radio does only ESP-NOW and the channel-6 softAP. Stored credentials stay in NVS throughout. The policy is `StaJoin` (`net/sta_join.hpp`, pure, natively tested); `WifiLink` carries it out. Each attempt first runs an async active scan of channel 6 only (`WiFi.scanNetworks` with the channel and the stored SSID as filters, 120 ms dwell, bounded by a 5 s timeout; a result on another channel is ignored). Only when the SSID is found there does the wisp call `WiFi.begin(ssid, pass, 6, bssid)` with the strongest BSSID the scan saw; not found counts as a failure with no wider scan. The channel argument to `WiFi.begin` is only where the driver's own scan starts, so the pre-scan is what keeps a missing or off-channel AP from triggering an all-channel scan; the driver can still scan further if the AP vanishes between the two. Attempts are judged by WiFi events, never by `WiFi.status()`, which the Arduino core latches from the last event: an STA disconnect the wisp did not cause (any reason but `ASSOC_LEAVE`) or 15 s without `GOT_IP` fails a join, and a `GOT_IP` in any wanted state is adopted, the core's one-shot first-connect retry included, except while halted by the channel guard; a `GOT_IP` while halted or while the source does not want the network is dropped at once, since that retry ignores `setAutoReconnect(false)` and can link after the wisp has left Osc. Disconnects and `GOT_IP`s are applied in the order they happened, and any that arrived before the wisp's own last drop are ignored, so a `GOT_IP` for a link already dropped is never adopted; the channel guard checks the channel each adopted `GOT_IP` carried. While linked, the STA netif's connected bit (not latched like `WiFi.status()`) backs up the disconnect event. The core's auto-reconnect is off; failures retry on a backoff (`RetryBackoff`: 10 s, doubling to a 5 min cap), restarted on entering Osc and on `setWifi` / `wifiReconnect`, and a lost link retries after 10 s. An AP that is not there therefore costs one single-channel scan per backoff step rather than an all-channel scan every few seconds, which is what pulled the radio off the mesh long enough for lamps to age out of the roster. The status does not say which network the wisp is failing to find; `[wifi] <ssid> not on ch 6; retry in Ns` on the console does. A drop re-pins the radio to channel 6 only when it has actually left it, since the driver refuses a channel change while scanning, connecting or serving softAP stations.

**Channel-6 STA guard.** The wisp shares one radio between ESP-NOW (pinned to `LAMP_ESPNOW_CHANNEL` = 6) and its STA join. Associating to an AP on any other channel drags the radio off 6 and silently breaks the mesh. On a `GOT_IP` whose channel != 6 the wisp refuses to stay associated: it drops the association, re-pins the radio to channel 6, and halts retries (so association churn can't re-drag the radio). It does not retry on its own. Recovery is an explicit `wifiReconnect` or `setWifi`, re-entering Osc, or Ethernet going down in Osc (the join becomes wanted again, see When the STA joins); each clears the halt and the flag. The first three are operator acts; the Ethernet edge is not, so a wisp whose cable drops retries the join once per drop. With every join made to a BSSID found on channel 6 this fires only if the AP moves channel after the join. The drop flips `wifiChannelMismatch` on and triggers an immediate `wispStatus` re-emit (no waiting for the 30 s heartbeat). Only the recoveries above clear it, each re-emitting the status.
- **`setDrift`**: sets the color-drift cadence. `intervalMs` [30000..3600000]: how often each lamp is re-targeted in milliseconds. `fadePct` [0..100]: how long each re-target fades. Every drift step draws its fade at random from 20 s up to 20 s + (`intervalMs` − 20 s) × `fadePct` / 100 (`driftFadeMs` in `paint/drift.hpp`), so 0 fades every step over 20 s and 100 lets a step take up to the whole interval. Reported back as `driftFadePct`. Persisted to NVS; reflected in the next `wispStatus` broadcast under `driftIntervalMs`/`driftFadePct`.
- **`setSwatches`**: `{"char":"wispOp","op":"setSwatches","swatches":true,"seq":812}`. `swatches` must be a JSON bool; missing or any other type is `Malformed` and changes nothing. An optional `seq`, an integer in 1..65535, is echoed in the status as `swatchesSeq` (see the wispStatus fields); any other value or no key means none and clears the echo. A wisp that predates it ignores the key. Picks how lamps take colours from the palette in every source mode (see the palette style under "Wisp paints a lamp's base + shade"). Persisted to NVS (key `swatches`, u8, anything but 1 loads as gradient); reported back as `swatches` in `wispConfig`. Gated like every config op: sealed once a password is set. A value that changes the style re-assigns every claimed lamp at once, as `shuffle` does (fade 0, so lamps jump and any drift fade in flight ends), re-emits ArtNet and redraws the ring; the same value again only bursts the status. An older wisp answers it as an unknown op (`Malformed`). The app sends it from the Gradient | Swatches switch, shown under Manual and OSC only for a wisp whose `wispConfig` carries `swatches` (`WispStatus.paletteStyle`), and confirms it on a `wispconfig` read from that wisp showing the new value under a `configLastSeenMs` other than the one held at the send (`WispNotifier.setPaletteStyle`), so a config the lamp held from before the pick never confirms it, since an earlier pick may still land after it. The switch shows the pick at once and holds it over every status and any config read still showing the old value; each attempt waits 10 s (the config read-back after a settings write lands inside it), four attempts. A pick equal to the wisp's held value at the send never confirms early, since no config of its own need follow and another setting's change would move the stamp: it resends for the whole budget, covering a late earlier pick, and then stands if the held value still matches. Any pick whose attempts all go unconfirmed stands if the held value matches it by then, and otherwise goes back to the held value with "Couldn't reach the wisp. Try again." A newer pick supersedes an older one, which stops resending, and a pick stops resending once a status comes from another wisp, even one a pending `setSource` holds off, and counts as unconfirmed. A source change that fails restores its snapshot with a pending pick still laid over it.
- **`setName`**: sets the wisp's display name, clamped to 20 characters. Persisted to NVS (key `wispName`). Reflected in the next `wispStatus` broadcast under `name`.
- **`setPassword`**: sets or clears the wisp control password. Persisted to NVS (key `wispPassword`). When factory-fresh (no current password), a plaintext `setPassword` is accepted. When a password already exists, `setPassword` must arrive sealed under the OLD password; the decrypt step authenticates the caller before the password is replaced. An empty `"password"` field clears the password (removes the NVS key), reverting to open access.
- **`setManualPalette`**: always accepted plaintext, even when a password is set (integrity exception; see framing note above). `colors` entries are `[r,g,b]` or `[r,g,b,w]` tuples (missing `w` reads as 0). An optional `seq`, an integer in 1..65535, is echoed in the status as `manualSeq` (see the wispStatus fields); any other value or no key means none. A wisp that predates it ignores the key, and an app that predates it sends none, which clears the echo. The wisp stores at most 16 colors (`kManualPaletteMaxColors`, the most a Straylight palette carries) and keeps the first 16 of a longer list; a longer palette stored before the cap loads as its first 16 (`WispConfig::begin` reads the blob whole, since `Preferences::getBytes` reads nothing into a shorter buffer), though NVS keeps the longer blob until the next save. The app's editor holds at most 16 (`WispRepository.kManualPaletteMaxColors`), and the op sends and the app hashes only the first 16. The app collapses `w == 0` colors to triples. The phone-to-lamp write is one BLE attribute, which the lamp's NimBLE takes up to 512 B (`WispRepository.kWispOpPayloadCap`, `BLE_ATT_ATTR_MAX_LEN`; on Android the app's BLE plugin refuses a longer write before sending), below the 576 B `CONTROL_MAX_PAYLOAD` relay cap every lamp from 1.1.1 accepts. The widest op, 16 colors with W on every one and the widest `seq`, is 352 B and goes out whole. A lamp on 1.1.0 relays at most 230 B, so a W-heavy palette of 10 or more colors never leaves it. Updates the wisp's stored palette; triggers a `MSG_WISP_PALETTE` broadcast.
- **`pollStatus`**: asks the wisp to re-broadcast `wispStatus` (+ `MSG_WISP_PALETTE`) once, without the op burst (see wispStatus cadence); changes no state. The app fires it on wisp-screen open (rate-limited app-side; coalesced wisp-side). Always accepted plaintext (read-only; see framing note above). Wisps that predate the op treat it as unknown → `Malformed` → no-op, so it degrades to the 30 s heartbeat.
- **`pollConfig`**: asks the wisp to re-broadcast `wispConfig` now; changes no state and does not re-emit the status. The app fires it beside `pollStatus` on wisp-screen open (rate-limited app-side; coalesced wisp-side, see `wispConfig` cadence). Always accepted plaintext. Wisps that predate the op treat it as unknown → no-op.

### Tier 3: Transient overrides

All four override/restore messages share the same prefix through `sourceKind` (bytes 0..19). `fadeDurationMs` follows at offset 20: **4 LE bytes** for `MSG_OVERRIDE_COLORS`, **2 LE bytes** for the other three. Only the tail after the fade differs.

**`MSG_OVERRIDE_COLORS` (0x21)**, **retired** as the wisp paint path (wisp paint is now declared in `MSG_WISP_STATE`); no live sender. Format + parser kept for backward-compat. Push transient colors onto a renderable surface.
```
header(6) + sourceMac(6) + targetMac(6) +
surface(1) + sourceKind(1) + fadeDurationMs(4 LE) +
numColors(1) + colors[numColors × 4 RGBW]
= 25 + 4N bytes (= 33 for N=2)

surface:        0x01 Base, 0x02 Shade, 0x03 BaseAndShade
sourceKind:     0x01 Wisp, 0x10+ user-defined
fadeDurationMs: u32 LE. 0 = instant snap; otherwise lamp-side
                duration-controlled fade via ConfiguratorBehavior.
                Range up to ~1hr (3,600,000 ms) for wisp color-drift fades.
numColors:      1..8 (kMaxOverrideColorsPerFrame, single source of truth)

surface = 0x03 (BaseAndShade) carries TWO RGBW colors in a single frame:
colors[0] → base, colors[1] → shade.
```

**Paint hold (STATE-driven)**: the wisp sends no per-lamp paint unicast and
runs no per-lamp keep-alive, and it retries no unicast that FAILs. The space-dim
brightness walk (`MSG_OVERRIDE_BRIGHTNESS`) is its only unicast, re-asserted
every 40 s inside the lamp's 60 s watchdog. `PaintDistributor` samples a per-lamp base/shade color
(deterministic per-MAC for a fresh paint, re-rolled per drift slot) and writes
it into the `WispRoster` claim — no wire send. `MSG_WISP_STATE` then broadcasts
the whole claimed set on its cadence, and a lamp holds paint while STATE keeps
naming it (see `MSG_WISP_STATE`). This drops the paint traffic from O(N) unicast
per cycle to one O(1) broadcast. A fresh paint shows at once. A drift step fades
linearly on the wisp over `driftFadeMs`, from the colors the claim carried at
that moment (`WispRoster::setLampDrift`), and each STATE frame packs the colors
as they stand plus the step's target and time left in the drift fade trailer
(see `MSG_WISP_STATE`). A lamp that reads the trailer runs the fade itself,
continuously. A lamp that doesn't, and one whose record misses a partial frame
with no fade running, eases to each frame's colors with its own short ease, so
the fade reaches it in steps of one STATE frame (2 s).

**`MSG_RESTORE_COLORS` (0x22)**, **retired** (STATE-absence eases a lamp home). Drop colors override, restore baseline.
```
header(6) + sourceMac(6) + targetMac(6) +
surface(1) + sourceKind(1) + fadeDurationMs(2 LE)
= 22 bytes

surface is Base/Shade/BaseAndShade (0x01/0x02/0x03); any other value,
0xFF included, is rejected by the parser. The wisp restores with
BaseAndShade (0x03).
targetMac == FF:FF:FF:FF:FF:FF means "restore on every lamp"
sourceKind == 0xFF (OverrideSource::Any) means "restore from any source"
```

**`MSG_OVERRIDE_BRIGHTNESS` (0x23)**, Push a transient relative-brightness factor 0..100.
```
header(6) + sourceMac(6) + targetMac(6) +
surface(1) + sourceKind(1) + fadeDurationMs(2 LE) + brightness(1)
= 23 bytes

surface is Base/Shade/BaseAndShade (0x01/0x02/0x03); any other value,
0xFF included, is rejected by the parser.
```

`brightness` is a relative factor: output = min(baseline, max(baseline × factor / 100, 20)), where baseline is the lamp's own current effective brightness. It scales, never raises: a lamp already below 20% is left as-is. The floor is a 20% output clamp enforced lamp-side at apply, so a forged factor=0 frame still lands at 20% output — nothing blacks out a space.

Source-gate: a lamp accepts a brightness override only from the wisp that currently claims it (fresh `MSG_WISP_CLAIM` in the display slot). The wisp broadcasts claims every other 2 s presence tick (~4 s) in every source mode incl Off, so the gate holds even when the wisp paints no colors. A rogue broadcaster cannot dim your lamps. The wisp re-asserts brightness by walking its claimed lamps with unicast `MSG_OVERRIDE_BRIGHTNESS` on a cadence under the 60 s override watchdog, plus an immediate walk when the operator moves the slider.

**`MSG_RESTORE_BRIGHTNESS` (0x24)**, Drop brightness override.
```
header(6) + sourceMac(6) + targetMac(6) +
surface(1) + sourceKind(1) + fadeDurationMs(2 LE)
= 22 bytes
```

**Fade behavior on receivers:**
- Fade happens in `ConfiguratorBehavior::draw` (single source of truth for per-pixel interpolation). Override modules set the target colors + `fadeDurationMs` once at apply-time.
- Mid-fade interrupt: a new OVERRIDE arriving during an in-flight fade snapshots the current interpolated buffer as the new "from", smooth handoff, no visual jerk.
- Watchdog auto-restore uses a sensible default fade (~1 s) since no sender supplied one. The colour `ColorOverride` watchdog is inert now that wisp colour rides `MSG_WISP_STATE` (no `MSG_OVERRIDE_COLORS` sender); STATE freshness is the paint hold. The brightness watchdog stays its own separate 60 s constant (`brightness_override.hpp`) — its 40 s unicast re-assert walk keeps it well inside that window.
- Brightness uses a change-driven callback: `BrightnessOverride::tick` invokes the registered callback only when the integer-rounded value actually changes, no per-frame `setBrightness` regression.

### Tier 4: Expression announce

**`MSG_EVENT` (0x30)**, shared-key-authenticated, nearby-scoped expression-fired announce.

```
[header(6)] [sourceMac(6)] [payload(1..230) — ExpressionInvocation JSON] [command_auth tag(8)]
```

- **Sender**: any lamp that fires an expression locally, via `MeshLink::sendEvent()`. Emitted for every local fire of a triggered (non-`continuous`) expression; not gated on `cascadeEnabled`. Continuous descriptors never announce — they retrigger at boot, settings upsert, and wisp release, and observers (the expression mirror) would spuriously replay those.
- **Receiver**: delivers to the `ExpressionObserverRegistry` fan-out on Core 1. No auto-action in the mesh layer; observers react if registered. Two consumers: the fondness engine's feed (`core/lamp.cpp`, [`social.md`](social.md#fondness-engine)) scores the sender's energy and overlap, and the `SocialEchoObserver` (expression mirror) probabilistically replays a warm peer's triggered expression ~0.5 s later, weighted by disposition + social mode. The replay goes through `triggerInvocation` (cascade-suppressed). A copy short of `ContagionTuning::chainMaxHops` (3) then sends its own MSG_EVENT carrying `hp` one higher, and a frame at the max is never copied, so a chain ends within 3 hops of its origin. See [`expressions.md`](expressions.md#expression-mirror).
- **No relay**: nearby-scoped by design — lamps only observe expressions they can physically hear.
- **Auth**: `command_auth::verify()` runs before dedup-record, so an unauthenticated frame is dropped before it consumes a dedup slot. See the command_auth section below.
- **Dedup**: `eventDedup_` 32-slot ring per `(sourceMac, seq)`. Originator pre-records its own seq so the broadcast echo does not re-deliver via observers.
- **Drain**: Core 1 loop via `PendingEvent` slot → `Lamp::drainEvent()` → `deliverEvent()` (`core/moments.cpp`): a payload carrying `mo` goes to the Moment director, anything else to `ExpressionObserverRegistry::fanOut()`.
- **Payload**: `ExpressionInvocation` JSON (cascade keys stripped, colors packed — see MSG_COMMAND). `delayMs` is carried but not acted on by the receiver; observers interpret it as they see fit.
- **`hp`**: optional top-level uint, the copies between this frame and the lamp that first fired it (`ExpressionInvocation::hops`). Written only when nonzero, so an origin frame carries no `hp`; an integer up to 4294967295 clamps to 255, and anything else (missing, negative, fractional, larger, a string) reads as 0. An additive key: no protocol bump, since `parseInvocation` ignores unknown keys, and a lamp that predates it copies terminally. A copy whose frame with `hp` would exceed `EVENT_MAX_PAYLOAD` still plays and is not announced. MSG_COMMAND parses the key too and does not act on it.
- **Moment frames**: `{"type":"moment","mo":{...}}`, a sentinel invocation carrying one extra top-level object, `mo`: `k` kind (1 Fireflies, 2 Whisper; any other is ignored), `s` uint32 seed, `a` age in ms since the sender's reference instant (0 to 2000; the Fireflies `t0`, or the Whisper sender's glow, which the next hop follows by 3 s), and for a Whisper `h` hops (1 to 8), `to` the next hop's MAC, `v` the visited MACs (12 uppercase hex each, no separators, exactly `12*h` chars, origin first) and, optionally, `c` the origin's base colour (`rrggbbww`, packed lowercase hex like `colors`; any other form drops the frame). Every frame is sent twice 200 ms apart. The worst case is 198 B. A frame carrying `mo` never reaches the mirror. An older lamp parses it as an invocation of the unknown type `moment` and renders nothing (its mirror may spend a roll on it); no variant registers that id. No protocol bump: the key is additive and `parseInvocation` ignores unknown keys. Contract: [`moments.md`](moments.md).

**`MSG_COMMAND` (0x31)**, shared-key-authenticated, targeted expression invocation from one lamp to a specific nearby lamp.

```
[header(6)] [sourceMac(6)] [targetMac(6)] [payload(1..1444) — ExpressionInvocation JSON] [command_auth tag(8)]
```

- **Sender**: any lamp, via `MeshLink::sendCommand()`.
- **Receiver**: applies locally only when `targetMac == myMac || broadcast`. No gossip relay.
- **Auth**: `command_auth::verify()` runs before dedup-record. See the command_auth section below.
- **Dedup**: `commandDedup_` 64-slot ring per `(sourceMac, seq)`.
- **Drain**: Core 1 loop via `PendingCommand` slot → `Lamp::drainCommand()`.
- **Payload**: `ExpressionInvocation` JSON. `delayMs` in the invocation is honored (enqueued to `pendingTriggers` if non-zero). `sourceMac` propagates to `triggerInvocation` for cascade coalescing. A tinted flicker burst that also carries `fadeDuration`, played at once, books a base tint from the same `sourceMac` that starts once the burst is reaped ([`moments.md`](moments.md), "Spore tint").
- **Payload ceiling**: `COMMAND_MAX_PAYLOAD` is 1444 B, derived off the ESP-NOW v2 frame (`ESPNOW_V2_FRAME_MAX` = 1470) less the 18 B fixed head and 8 B tag. MSG_COMMAND is a physical broadcast, so a frame over the classic 250 B limit reaches only v2-capable peers; a v1/classic peer drops the oversized frame per the ESP-NOW contract and silently misses that cascade (graceful, no crash). Big cascades therefore reach only the v2 fleet until every peer runs the v2 firmware; a mixed-fleet capability gate is owed before public beta.
- **Colors encoding**: `colors` is a single packed lowercase-hex string, 8 chars per color (`"rrggbbww…"`), no `#`, no separators; the key is omitted when empty. A receiver drops a malformed `colors` string whole (length not a multiple of 8, or a non-hex char) and still applies the invocation with its configured palette. A receiver keeps at most the first 8 colours and 12 `parameters` keys it knows (`kMaxExpressionColors` / `kMaxExpressionParams` in `config/config_types.hpp`) and ignores the rest, the same caps a stored expression carries. Example:

```json
{"type":"glitchy","target":3,"delayMs":0,"colors":"ff00000000ff0000","parameters":{"durationMin":250,"durationMax":900}}
```
- **Known senders**: cascade fan-out (`ExpressionManager::maybeCascade`), and the app's Test, once it has played on the lamp and when its parameters set `cascadeEnabled`; snafu `Greeting::control()` on peer arrival — sends a fast glitch (`type="glitchy"`, `durationMin=durationMax=12`, `target=SHADE`) colored with the sender's stem first color (`config.base.colors[0]`). Only sent when the peer has a known ESP-NOW MAC (`hasMac=true`). A mushroom sends a spore as a broadcast-targeted command signed with the lamp key: `{"type":"flicker","target":2,"colors":"00ff8000","parameters":{"count":12,"durationMax":6000,"fire":0,"opacity":60,"fadeDuration":120}}`.

### command_auth: shared-key tag on EVENT + COMMAND

MSG_EVENT and MSG_COMMAND are the two "force another lamp to do a thing" types, so both carry an 8-byte trailer: `HMAC-SHA256(key, frame_body)[:8]`, where `frame_body` is everything before the tag. `command_auth::appendTag()` writes it on send; `command_auth::verify()` checks it on receive, before the dedup-record, so a bad tag is dropped before it consumes a dedup slot. `MSG_CONTROL_OP` carries wisp control (a sealed wispOp the wisp decrypts) and does not use this.

The 32-byte key is baked in at build time from `LAMP_COMMAND_KEY_HEX` (a 64-char hex `-D` define). Key injection tracks the channel: `scripts/inject_command_key.py` injects nothing on a **dev** build (keyless/bench), and on **beta**/**stable** resolves the key from `LAMP_COMMAND_KEY_HEX` or `~/.lamp-os-command-key.hex`, FATALing if it's missing. Signed CI builds get the key via the `LAMP_COMMAND_KEY_HEX` secret.

- **Keyless build** (no key compiled in): `appendTag()` writes 8 zero bytes so the frame stays a uniform size that keyed peers still parse, and `verify()` returns true (can't verify => permissive). Dev builds mesh and cascade normally.
- **Keyed build**: `verify()` accepts only a constant-time match. A keyed lamp drops EVENT/COMMAND from a keyless dev build because its tag is zeros.
- **Not secrecy**: secure boot is off and the signed binary is public, so the key is extractable by a determined binary-reverser. This stops firmware built from source without the key, not a reverser.

**No PROTOCOL_VERSION bump.** The tag rides as an additive frame extension — older parsers ignore the trailing bytes, and a bump would instead make mismatched peers invisible to each other, splitting the mesh for no benefit. A keyed lamp only ever drops a dev build's EVENT/COMMAND, which isn't trusted to force other lamps anyway.
**`MSG_COLOR_QUERY` (0x32)**, Directed request for a peer's full color info (base + shade gradient stops).

```
[header(6)] [sourceMac(6)] [targetMac(6)]
```

Fixed 18 bytes; no payload. No gossip relay; addressedToUs filter on recv. A received query waits in a 4-deep queue (`pendingSlots.colorQuery`, a `PendingTypedQueue`) for the loop to answer, so two askers before one drain both get a reply; a query landing on a full queue is lost with its resends (LAMP_DEBUG `[queue.full]`).

**`MSG_COLOR_INFO` (0x33)**, Directed reply to MSG_COLOR_QUERY carrying base + shade gradient stops.

```
[header(6)] [sourceMac(6)] [targetMac(6)] [baseCount(1)] [base RGBW stops (baseCount*4)] [shadeCount(1)] [shade RGBW stops (shadeCount*4)]
```

- Each stop is 4 bytes RGBW (R, G, B, W). baseCount and shadeCount are each ≤ 8. Maximum frame size is 84 bytes.
- No gossip relay; addressedToUs filter on recv. Replies queue the same way (`pendingSlots.colorInfo`, 4 deep) and the loop delivers every queued one each tick.

## BLE GATT characteristics (lamp ↔ phone)

Service UUID `5f64f4d0-d6d9-4a44-9b3f-3a8d6f7e6b40`. UUIDs share that base; the `(0xNN)` shorthand below is the distinguishing 4th byte (`5f64f4NN-…`), except `commit` which uses an unrelated UUID. AES-GCM-gated characteristics require a successful `CHAR_AUTH` write within the connection lifetime.

**The layout is a frozen, positional contract.** `kGattLayout` in [`gatt_layout.hpp`](../../software/lamp-os/src/components/network/ble/gatt_layout.hpp) is the single source of truth and lists characteristics in **registration order** — handles are positional, so that order *is* the contract (`ble_control.cpp` registers by iterating the table, so order and props cannot drift; a boot-time coverage check flags a callback binding that misses the table). Grow append-only at the tail or evolve a payload; never insert/remove/reorder/add-a-CCCD without bumping `kGattSchemaVersion` (currently **4**) and re-pinning the hash in `test_ble_gatt_layout`. See the frozen-layout lock-in in `CLAUDE.md`. The table below is in layout order.

**Auth + state notify:**
- `CHAR_AUTH` (0xd1), write: lamp password (ciphertext or plaintext). Gates every auth-gated characteristic for the connection's lifetime.
- `CHAR_STATE_NOTIFY` (0xd8), notify: lamp-driven state-changed notifications. JSON payload includes `previewActive` (bool), a `greeting` object, and `nearbyRev` (uint32). `greeting.active=false` when idle; `greeting.active=true` carries `peer` (the greeted peer's `lampId`, mesh mac) and `kind` (`"warm"` / `"reserved"` / `"snub"` on standard lamps; `"glitch"` on snafu). Edge-triggered: fires on greeting start and stop. `quiet` (bool) is `ota_quiet_mode::isQuiet()`, the predicate every live-control write gate tests: true exactly while the lamp drops every write on this service except `CHAR_FW_CONTROL` / `CHAR_FW_CHUNK` and a `CHAR_EDIT_SESSION` 0x08 close (page-protocol reads still work). The lamp notifies on each change of it while a client is connected with notifications on, when that client subscribes, and on connect once it has; it sends only to the connected client's connection, and only while that client is subscribed (`sendStateNotify`). One of those the lamp had no heap to build, or NimBLE could not queue (no mbuf), goes again 100 ms later (`StateNotifyTrigger::kRetryMs`) until one goes out or the client leaves or unsubscribes; a send NimBLE queued and lost afterwards (the link drops) is not seen. The subscription dies with the link, so the app re-subscribes after every reconnect. Firmware before the field omits it. Whenever the lamp reports `quiet: true` outside a push from this app, including a lamp reopened while an earlier session's push still holds it quiet, the app freezes editing until `quiet` reads false, then sends its session flags again (`CHAR_HOME_MODE_FOCUS`, each `CHAR_EDIT_SESSION` selector it set) and, if no quiet freeze was running when the report came, re-reads the control sections (`lamp`, `base`, `shade`, `home`, `expr`). An app push decides the same way when it ends without a reboot (or the local verify ends): frozen if the lamp still reports quiet, re-synced at once if it reported quiet during the push and is listening again, and with only the flags a new link still owes if it never reported quiet (a declined offer). The freeze ends after `ControlNotifier.quietAfterPushBound` (75 s) from the push end or the latest `quiet: true`, regardless: the receiver's no-progress abort (`kNoProgressAbortMs`, 60 s) plus its inter-session hold (`InterSessionQuietHold::kHoldMs`, 10 s), plus slack. The app sends each flag it holds open as soon as a new link comes up, on any firmware, then subscribes as the last step, so the on-subscribe report arrives after the connected state. A lamp that reports `quiet: true` on that link gets the flags again once it reports `quiet: false`. If the app last heard the lamp report `quiet: true` (on the link before, or with a quiet freeze still running), only a held Social open (see `CHAR_EDIT_SESSION`) goes at once and the rest wait for `quiet: false`. Otherwise a lamp that reports `quiet: false` gets nothing more. A lamp without the field gets the flags only from the send on each new link, the re-read when a push that reached it ends (not a declined or already-current offer, nor a failed local verify) and the focus ahead of each `CHAR_BRIGHTNESS` write until the next reconnect. `nearbyRev` bumps when the `nearby` section's app-visible fields change (everything the section emits except `lastSeenMs` and `rssi`, which churn ~30 Hz on every BLE adv), coalesced to the same ≤1 Hz roster-rebuild cadence, and also bumps each time the list is built afresh after it was freed; it holds still while the list is not built. The app re-reads `nearby` on a bump instead of polling.

**Slider-rate write channels (write / no-response, ~30 Hz):**
- `CHAR_BRIGHTNESS` (0xd2), write+wnr: 1 byte 0..100. Routed to `homeMode.brightness` while a Home-Mode edit session is focused.
- `CHAR_SHADE_COLORS` (0xd3), write+wnr: a JSON array of hex color strings (the broadcast segment), `{"seg":k,"colors":[...]}` (segment `k`), or `{"colors":[...],"rotate":{"on":true,"periodS":40,"dir":"up"}}`. Live preview into RAM config; nothing reaches NVS until `CHAR_COMMIT`.
- `CHAR_BASE_COLORS` (0xd4), write+wnr: a JSON array of hex color strings, or `{"colors":[...],"rotate":{...}}`. Same preview and commit rules.

  In the object forms `colors` is required and must be a non-empty array: an object without one is dropped whole, `rotate` included. `rotate` and each key in it are optional, and a key sets its value only when it has the right type: `on` a boolean, `periodS` an integer (read as 32-bit signed, clamped to 5..120 seconds per loop), `dir` the string `"up"` or `"down"` (physically up or down on that surface). A missing key, or one of another type or value, leaves that value as it was, and a write without `rotate` (the bare array, the `seg` form, the web config preview) leaves rotation alone. `rotate` applies only to a role with exactly one segment, and on the shade only with `seg` 0 or no `seg`; any other write applies its colours and ignores it. A shade `seg` that is not an integer 0-255 or names no segment the role has, or a base `seg` other than 0 (the base has no per-segment form), drops the write whole. Whether the variant renders rotation plays no part in what the write stores.
- `CHAR_BASE_KNOCKOUT` (0xd5), write+wnr: 2 bytes `[pixelIndex, brightness 0..100]`.
- `CHAR_HOME_MODE_FOCUS` (0xe5), write+wnr: 1 byte 0/1 — app sets 1 while the user is on the Home-Mode setup page (forces preview + reroutes brightness). Auto-cleared on connect and disconnect. Dropped in OTA quiet mode like every live-control write. While the Home-Mode page is open the app sends it on every new link, and again once a lamp that reported quiet reports `quiet: false` (see `CHAR_STATE_NOTIFY`).
- `CHAR_EDIT_SESSION` (0xe9), write+wnr: 2 bytes `[selector, state]`, `state` != 0 opens, all cleared on disconnect. `selector` 0x01 base / 0x02 shade / 0x04 brightness are the operator-priority lockout against wisp overrides. `selector` 0x08 is the Social/Network view flag: while set (app on the Social page), the lamp reopens a low-duty passive BLE scan during the connected session — short windows (~30 ms scan / 300 ms gap, ~10% duty), skipped for `idleGuardMs` after any throughput-sensitive write and bounded by a safety timeout — so BLE-only (non-mesh) peers keep being sighted into the roster and surface in the `nearby` section. The connect-time scan pause (which protects write throughput) otherwise stops those sightings for the whole session. Clearing 0x08 after an open on the same link also ends the `nearby` section's 30 s hold, so the lamp frees the list on its next loop tick. Both writes count during OTA quiet: an open there is not acted on (the scan waits for the app to send it again once `quiet` reads false) but still lets the close end the hold. A cleared flag the app replays, after quiet or a reconnect, ends nothing, so a mesh-lamps screen keeps its hold (`SocialView`). The app therefore sends a held open at once on every new link, before the lamp says whether it is quiet, so a close after a reconnect during quiet still ends the hold.

**Commit:**
- `CHAR_COMMIT` (`48537d49-…`), write+wnr: parameterless commit signal — the *arrival* of the write is the signal (bytes ignored). Flushes pending slider/color writes to NVS off the NimBLE host task; result returns via `CHAR_STATE_NOTIFY`. Also force-flushed on disconnect.

**Op channels (write):**
- `CHAR_EXPRESSION_TEST` (0xd6), write+wnr: utf-8 expression type, empty = complete.
- `CHAR_EXPRESSION_OP` (0xd9), write: `{op: upsert/remove, ...}` JSON.
- `CHAR_WIFI_OP` (0xda), write: `{op: scan/forget}` JSON.
- `CHAR_REMOTE_OP` (0xe4), write: encrypted JSON carrying a top-level `targetMac`. Applied on this lamp (`brightness`, `shadeColors`, `baseColors`, `knockout`, `expressionOp`, render only) when `targetMac` is this lamp's MAC or `"broadcast"`; any other target is logged and ignored, never forwarded. No current app writes it; the characteristic stays because the GATT layout is frozen.
- `CHAR_SOCIAL_DISPOSITIONS` (0xe6), read+write: per-peer disposition map (1..5).
- `CHAR_SETTINGS_BLOB` (0xd7), write: a partial settings JSON carrying any of `lamp`, `homeMode`, `base` and `shade` plus an optional `reboot` (default true), or the `{factoryReset: true}` sentinel alone (write path only; reads go through the page protocol below). Its `base` / `shade` strip format is `byteOrder` and a positional `segments[].px` and `segments[].pin` (a data GPIO, 0 for the variant's own pin, applied at the restart), which `apply::pixelFormatLocal` reads (the base and shade sections carry each segment's `pin`, 0 for the variant's own, and `builtinPin`, its strip's variant pin or 0 with no strip; the app offers the pin only when both are there); a role's `colors` are applied as a colour write and the base's `knockout` as a knockout write, and segment names and colours are ignored. The whole write, AES-GCM framing included, must fit one 512 B ATT value, so `writeSettingsBlob` in the app refuses a blob over it before writing, judged by its encrypted size even to a lamp without a password.

**Section reads — page protocol (replaces the former per-section read characteristics):**
- `CHAR_PAGE_CTRL` (0xdc), write: section name (`lamp` | `base` | `shade` | `expr` | `home` | `nearby` | `exprcat` | `wispclaims` | `wisppalette` | `wispstatus` | `wispconfig`). Snapshots that section's cached JSON (binary for `wispclaims` and `wisppalette`) into a per-connection buffer and resets the read cursor; `exprcat` is the exception — it points the read cursor straight at the flash-resident catalog (`kExprCatalog`), no per-connection copy. An optional trailing byte caps the chunk MTU.
- `CHAR_PAGE_DATA` (0xdd), read: returns the next chunk of the snapshot and advances the cursor. The app reads repeatedly until an empty chunk signals end-of-section (`readPagesUntilEmpty`); a short chunk is not the end, since the chunk size follows the link MTU. Per-connection cursor state, so concurrent phones don't collide. The read that serves the empty end-of-section chunk, and the next section's open, free that connection's copy when the section is over `SectionPage::kKeptCapacity` (1 KB) or its buffer is over twice that, so a large section (`nearby`, a big `expr`) stays held between reads only while it is read; a smaller section keeps its buffer for the connection, so a re-read of a section no larger than it copies into that buffer with no heap check. A small section read right after a large one starts from no buffer and needs the heap check (`heapCanSpare`, its size plus the 4 KB headroom), so on a tight heap it can read `!`. A reader that stops a large section early holds its buffer until it opens another section (an unknown name included), or until it disconnects.

An unknown section name clears the snapshot, so its first DATA read is empty; so is any read before the auth handshake. The wisp sections lean on that: `wispstatus` serves the `CHAR_WISP_STATUS` merge whole (no 512 B ceiling, nothing shed) and `wispconfig` the cached `wispConfig`, and both answer at least `"{}"` on a lamp that has them. The app reads `wispstatus` first and falls back to the direct `CHAR_WISP_STATUS` read when it comes back empty; one non-empty read marks the lamp as serving both, and so does any notify carrying `configLastSeenMs`, which only such a lamp merges, so a build whose reads all landed before the auth handshake still finds the sections. One residual: a status still over 512 B after shedding notifies an empty value, which carries no `configLastSeenMs`, so an app that has not yet marked the sections cannot recover that update from them. The app keeps showing the last good status meanwhile, since it drops an empty notify as transient; the next status that fits recovers it, or leaving the lamp and opening it again, whose fresh notifier re-runs the section read (a reconnect keeps the notifier). Reopening the wisp screen does not: the lamp shell keeps the notifier alive, and the screen's polls only bring more empty notifies. `wisppalette` serves the cached manual palette raw (interleaved R,G,B,W), off the notify-clobbered status. `wispstatus` builds its JSON on the NimBLE host task, as the direct `CHAR_WISP_STATUS` read always has; the others copy a cached payload out under the roster mutex. A wisp-status build the heap cannot spare (`LampRoster::getWispStatusReadJson` refuses below twice `kWispStatusCharMaxLen` plus the 4 KB headroom, or catches a failed allocation) reads empty on both paths and skips that notify, logged as `wispStatus OOM` at most every 5 s.

A config section (`lamp`, `base`, `shade`, `expr`, `home`) the lamp cannot build or copy out for want of heap reads as the single byte `!` (`SectionPage::kBusy`, served from flash with no allocation), never as empty bytes, which would read as a link that has not authenticated, and never as a copy from before a rebuild that failed. The app reads it again a few times, then shows that the lamp is low on memory with a retry. An app that predates the marker fails to parse it: on opening the lamp it shows its connect error, and on a reconnect it keeps the last values on screen until its reconnect ladder gives up; it never shows the password prompt or applies defaults.

The `lamp` section is a JSON object of the lamp's own identity + settings: `name`, `brightness`, `password`? (only when set), `hasPassword`, `advancedEnabled`, `webappEnabled`, `brightnessCeiling`, `socialMode`, `fwVersion`, `fwChannel`, `catalogHash` (8-char hex FNV-1a over the flash expr catalog bytes, precomputed at build time; the app caches the `exprcat` payload per-hash and re-reads only when it changes), `lampType`, `lampId`? (this lamp's own mesh mac, canonical uppercase colon-hex via `formatBdAddr`, the same bytes peers store for it as `lampId` in their `nearby` section; omitted until the mesh link has come up), `otaState`? (this lamp's own OTA state, 0/1/2 = idle/sending/receiving, omitted when idle; same values as the `nearby` section's per-peer `otaState`), `otaSendingTo`? (the distribution target's mesh mac, canonical uppercase colon-hex; present only while `otaState` is sending, same field/semantics as the `nearby` section's per-peer `otaSendingTo`), `resetReason` (this boot's `esp_reset_reason_t` ordinal), `lastCrash`? (the persisted crash record, omitted until the lamp has crashed once; see [`embedded-heap.md`](embedded-heap.md#reading-a-crash-record)). `lampId` lets the app match a lamp against how its peers observe it. The webapp's `GET /api/settings` serves a different document: the full persisted config (`Config::asJsonDocument()`, with `lamp` / `base` / `shade` / `expressions` / `homeMode`), password stripped. Its `base` and `shade` objects carry `rotate` in the stored shape: for any one-segment role whose rotation differs from that role's default, whether or not the variant renders rotation, so the PUT carries it back. Its `lamp` object carries the stored settings plus `hasPassword`, `lampId`, and one webapp-only field, `apSecured`, whether the setup softAP came up WPA2-keyed with the lamp password (which needs 8-63 characters). The firmware-identity and runtime fields above (`fwVersion`, `fwChannel`, `catalogHash`, `lampType`, `otaState`, `otaSendingTo`, `resetReason`, `lastCrash`) are BLE-only. `apSecured` and `hasPassword` are both GET-only there; a PUT saves through the config model, which has no such fields. The PUT takes `application/json` (415 otherwise) of at most 16 KB (413 over it; 400 with no body), gathered into one block (500 when the heap cannot spare it, when the heap check before the parse refuses it, or when the parse runs out of memory) and parsed once, on the loop: a body that is not strict JSON (a single-quoted string, an unquoted key or bare word), has no `lamp` object, or carries a password or SSID over its cap is answered 400, and one sent while an earlier save waits for its reboot 409. The loop takes no web save while a firmware update is being received. `GET /api/dispositions` answers 503 when the lamp cannot spare the heap to build the map, never an empty `{}`, which the editor would show as every peer Neutral. The BLE social-dispositions read answers `!` for the same reason, and the app writes no map back after a read that was not a JSON object. Those answers come while the handler waits for the loop (3 s); a save still running then is answered 202 and any refusal after that is only logged. When a password is set that cannot key the AP, the webapp's write routes and `/api/unlock` answer 403: an open network must not hand out config writes or the password itself.

The `base` and `shade` sections carry `rotate` (`{"on":…,"periodS":…,"dir":"up"|"down"}`, every key present) exactly when the role offers colour rotation: the variant sets `Config::Defaults::rotationSupported` and the role has one segment. Otherwise the key is absent, even when the role holds a stored rotation that is on, so the section never reports what the lamp will not render. Its presence is the app's whole signal that the role can rotate, as `colorsEditable` is for the colour picker. The section is rebuilt on commit, like the colours.

The `nearby` section is a JSON array of the lamp's roster, one flat object per peer: `name`, `lastSeenMs` (max of the two transport timestamps), `viaBle`, `viaEspNow`, `near` (`lastSeenNearMs` set and within `LAMP_PRUNE_TIME_MS`, the same test `LampRoster::snapshotNear` uses), `lampId`? (peer's mesh mac, canonical uppercase colon-hex; omitted when the roster entry has no mac yet), `rssi`? (omitted at the -127 sentinel), `shade`, `base`, `fwVersion`? (omitted when 0), `fwChannel` (peer's `{type}-{channel}` slot, JSON-escaped, empty string on legacy peers that never sent it), `otaState`? (omitted when idle), `otaSendingTo`? (the mesh mac of the peer it is sending firmware to, canonical uppercase colon-hex, present only while it sends). `shade`/`base` are 8 lowercase hex chars `rrggbbww`; the app also accepts the legacy 4-int RGBW array shape from deployed firmware. The array is capped to the `NearbyList::kMaxLamps` (25) most-relevant peers — near before mesh-only, then most-recently-seen, then strongest RSSI — so the contiguous build stays bounded regardless of fleet size; a crowd past that drops the farthest and stalest first (the app surfaces "there may be more"). The list (`NearbyList`, `components/network/ble/nearby_list.hpp`) is built only while the app reads it: a `nearby` page read stamps the time, the loop builds it on its next tick, and it is held while reads keep coming and freed `NearbyList::kHoldMs` (30 s) after the last one, or at once when no client is connected. Clearing the `CHAR_EDIT_SESSION` 0x08 selector (the app leaving its Social page) ends the hold (`NearbyList::endHold`), so the loop's next tick frees the list and the roster copy unless a read comes first; the mesh-lamps and wisp-painted-lamps screens send no 0x08 and keep the 30 s hold. The app reads it only on its Social, mesh-lamps and wisp-painted-lamps screens, and polls every 20 s while one is open, so a phone on any other screen costs no nearby list and no roster copy. The read never builds on the NimBLE host task: it waits up to `NearbyList::kReadWaitMs` (100 ms) for the loop's build, holding no lock, then copies the list out under a mutex; a list still not built then (low heap, a stalled loop) reads empty, which the app takes for a transient glitch and keeps its last list. A disconnect ends the hold, so a reconnect builds nothing until the app reads the section again. A list that shrinks while the heap cannot spare a smaller buffer renders into the one held. While built it is rebuilt when the roster's generation counter changed (at most once per second), rendered into the buffer it already holds; a measure pass counts the bytes the render will write, and a new buffer, of that length plus a 128 B slack, is taken only when the list outgrows the one held or falls 256 B short of it, and only that allocation waits on the largest free block. The roster copy behind it is sized to the roster's count. The webapp's `/api/nearby` copies the same list out and answers `[]` while it is not built, which is always while the webapp serves: serving tears BLE down (`deinitForWebapp`), and `ble_control::tick` maintains the list only while BLE runs.

**Mesh state mirrors:**
- `CHAR_WIFI_STATE` (0xdb), read+notify: JSON snapshot of WiFi/scan state. `scanResults` carries only the list of a scan the app requested (`op: scan`), held until the app disconnects; the lamp's own home-presence scans publish none. The lamp notifies only on a change, and the subscription dies with the link, so the app's Wi-Fi picker (`WifiNotifier`) re-subscribes after every reconnect, reads the value on the reconnect, and reads it again once each subscription's first frame shows the notify is enabled, so a change made while the link was down or before the enable is not lost. A notify that does not parse (such as a scan list cut off at the notify size) is logged and the value is read instead.

**Firmware OTA (phone → lamp):**
- `CHAR_FW_CONTROL` (0xe7), write+notify: app writes `MSG_FW_*` control frames (OFFER/DONE) in lamp_protocol wire format; the lamp's receiver replies via notify on this same characteristic.
- `CHAR_FW_CHUNK` (0xe8), write+wnr: high-frequency `MSG_FW_CHUNK` stream. The app sizes the chunk payload to the negotiated BLE ATT MTU (`min(mtu-3-26, FW_CHUNK_SIZE_MAX)`, floored at 200 when the MTU is low or unreported) and carries the chosen size in the OFFER's `chunkSize`, matching the receiver's per-session `offerChunkSize_`. The lamp drops a write here unless the receiver's session was opened over BLE (the transport rule in `checkFwChunk`, below), so an app connected during a mesh receive cannot write into the mesh image.

**Schema + claims:**
- `CHAR_SCHEMA_VERSION` (0xea), read: single byte = `kGattSchemaVersion`. Absent on legacy lamps that predate it (app falls back to legacy behavior). The app's link probe reads it as its one-byte liveness check, and reads the `lamp` section on a lamp without it; nothing in the app gates on its value yet.
- `CHAR_WISP_CLAIMS` (0xeb), read, auth-gated (schema v2, v4 tail): binary blob `[count(1)][lampMac(6)]×count[colorPair(6)]×count[painted(1)+baseW(1)+shadeW(1)]×count`, `WispFleetCache::kBlobEntrySize` (15) bytes per lamp, built by `WispFleetCache::buildClaimsBlob`. Membership is the de-duplicated union of the fresh accumulated `MSG_WISP_CLAIM` entries and the fresh accumulated `MSG_WISP_STATE` entries (same 60 s per-entry staleness window for both, capacity 100 each); claim macs come first, paint-only macs follow. This means a lamp that arrived via paint before its claim message is not invisible. `count = 0` when everything is stale. Split from `CHAR_WISP_STATUS` because that payload is already near the MTU budget.
  - **Sections**: `colorPair` is `baseRGB(3)+shadeRGB(3)` and the paint section is `painted, baseW, shadeW`, both positionally aligned to the macs. `painted = 1` when the mac has fresh paint from `MSG_WISP_STATE`; its colours are then exact, black included, with W from the STATE W plane. `painted = 0` when it has none, with all colour and W bytes zero.
  - **Compatibility**: every section is appended after the ones before it, so the GATT layout is unchanged. A reader that checks `length >=` for the sections it knows ignores the rest. An app that knows only `[count][mac][colorPair]` treats an all-zero pair as "no live colour, predict instead". `parseWispClaims` (app) uses the paint section when the whole of it is present (`length >= 1 + count×15`): a painted mac maps to its RGBW colours, black included, and an unpainted mac is omitted so the preview falls back to its predicted colour. Without a complete paint section (an older lamp, or a truncated read) it applies the older rule: RGB with W = 0, an all-zero pair omitted. A partial or absent colour section reads as the mac-only blob.
  - **Size**: a characteristic value over the vendored 512 B ATT ceiling reads back empty, so the direct read (`WispClaimsCallback`, what `WispRepository.readClaims` reads) builds into a 512 B buffer. `buildClaimsBlob` fits as many entries as the `[count][mac][colorPair]` layout holds (42) and adds the paint section only when it fits too (up to 34 entries); past 34 the read carries no paint section and the app applies the older rule. The `wispclaims` page section serves the same format from a buffer sized for `WispFleetCache::kCapacity` (100) entries with the paint section, and the same fit rule applies past that.

**Wisp proxy**:
- `CHAR_WISP_OP` (`5f64f4e1-...`), write, auth-gated. Sealed or plaintext payload unicast verbatim as `MSG_CONTROL_OP` to the paired lamp's display-slot wisp. The relay lamp passes the payload through opaque; the wisp handles decryption. No new wire-format msg type was added; the routing rides the existing `char`-tagged JSON envelope. Lamps do not apply it locally. See wispOp framing details above.
- `CHAR_WISP_STATUS` (`5f64f4e2-...`), read+notify, auth-gated. Returns the lamp's cached `wispStatus` JSON (sourced from gossip-relayed `MSG_CONTROL_OP` broadcasts the wisp emits) merged with the last `MSG_WISP_HELLO` data on file (`wispMac`, `wispVersion`, `helloFlags`, `helloPaletteIdPrefix`, `helloLastSeenMs`), `statusLastSeenMs`, and `configLastSeenMs` once a `wispConfig` is cached, capped at 512 B by shedding the diagnostics (see the wispStatus budget); the `wispstatus` page section serves it whole. Notify fires whenever a new wispStatus, a changed wispConfig or a palette lands on the lamp, when `MSG_WISP_STATE` starts or stops painting this lamp or moves the colours it heads to (`baseWispColor` / `shadeWispColor` are those heading colours, see the lamp drift fade under `MSG_WISP_STATE`), and on the presence edge when a `MSG_WISP_HELLO` first establishes (or a rival takes over) the display slot, so a wisp that comes online after the app connected surfaces live without an app restart. Steady-state 2 s keepalive hellos do not re-notify. The lamp caches exactly one wisp; admission is sticky-first-heard: a rival wisp's hello/status/palette/paint broadcasts are rejected until the current wisp misses 6 of its 2 s hellos (12 s window), except a `MSG_WISP_CLAIM` naming this lamp, which takes the slot immediately when the current wisp does not claim it. Adoption itself stamps the 12 s window, so a just-adopted wisp (claim takeover, first paint) is sticky before its first hello is cached and the displaced wisp's next broadcast cannot re-take the slot. This keeps two overlapping wisps from flip-flopping the app's wisp view at zone boundaries.

In steady manual mode STATE re-covers the whole claimed set every ~2 s, well
inside the `kWispStateFreshMs` (60 s) failsafe. The failsafe firing is the
silent-wisp path — a wisp that has actually gone away — not the normal hold.
An Off (or unclaim) eases the lamp home the moment the first fresh STATE omits
it, and a paint-mode edge emits STATE out of cadence so that lands promptly.

**Palette style** (`setSwatches`, `paint/tuple_sampler.cpp`). Every lamp's
pair, drift steps and the ArtNet fixtures included, comes from one sampler,
which the app's painted-lamps preview (`predictTuple`) must match byte for
byte (`predictTuple` and `predictTupleAtPositions` take the style; the app's `tuple_sampler_test.dart` mirrors the wisp's swatch vectors case for case); an app without swatches predicts gradient only. Per
lamp it draws two positions over the full `uint32` span, posA and posB, from
the lamp's MAC hashed with `shuffleSeed` (a drift step draws them at random;
ArtNet uses seed 0, so Shuffle never re-rolls ArtNet fixtures).

- **Gradient** (default): merge adjacent near-duplicate colours, keep posB at
  least a quarter of the span from posA, sample the blend at both, then swap
  base and shade on a third hash bit.
- **Swatches**: the palette as given, no merging. Base is entry
  `(posA × n) >> 32` of the n entries, so a colour repeated k times is the base
  on about k/n of the lamps. Shade is the `((posB × m) >> 32)`-th, in palette
  order, of the m entries whose RGBW bytes differ from the base, or the base
  itself when none do. No swap. Every lamp shows palette colours exactly; with
  two distinct colours every lamp shows the same pair. The wisp's ring draws
  the palette as solid blocks instead of a blend, and so does the app's palette
  bar (`renderPaletteBlocks`).

The combined-frame model (`surface=BaseAndShade, numColors=2`) packs
both surfaces into a single ESP-NOW frame. Delivery is atomic: both
colors land or neither does, so base and shade can't diverge from
per-surface frame loss under BLE coex.

**Observability**: the lamp's `[wispcoex]` meter
(`components/network/mesh/wisp_coex.hpp`, fed from `mesh_link.cpp`) logs a
periodic per-wisp `recv`/`maxgap` line on `LAMP_DEBUG` builds. `maxgap`
(wall-clock between hellos) climbing toward the `kWispStateFreshMs` (60 s)
failsafe is the signal that the STATE paint stream itself (not just hellos) is
at risk of a drop; see `qa/coex.md`. There is no `loss%`/`missed`: the wisp
shares one seq counter across all its message types, so a per-message-type
seq gap is not loss, and `maxgap` is the real presence-stability signal. The
STATE stream is measured by the `[wispstate]` meter
(`components/network/mesh/wisp_state.hpp`, fed from the `MSG_WISP_STATE` recv
arm and scoped to the display wisp): a 30 s
`[wispstate] win=30s recv=N adopts=A releases=R selfPresent=P` line
(piggybacked on the `[meshmix]` window) plus an edge-only
`[wispstate] ADOPT|RELEASE src=… seq=N` line on each paint transition (seq is
just the frame identifier there). Whether the lamp reliably sees the wisp
take / release control reads directly off the adopt/release edges and counts.

## Firmware-distribution messages (`MSG_FW_*`)

These carry the **lamp-to-lamp gossip OTA**: a lamp running newer firmware streams its running image to an out-of-date peer it meets on the mesh. Lamp↔lamp only, the wisp does **not** participate in OTA (it is USB-flash-only).

| Type | Direction | Purpose |
|---|---|---|
| `MSG_FW_OFFER` (0x40) | distributor → peer | "I have firmware version X for you" |
| `MSG_FW_ACCEPT` (0x41) | peer → distributor | "begin streaming" |
| `MSG_FW_CHUNK` (0x42) | distributor → peer | ordered firmware bytes |
| `MSG_FW_REQ` (0x43) | peer → distributor | retransmit request |
| `MSG_FW_DONE` (0x44) | distributor → peer | "verify now" |
| `MSG_FW_RESULT` (0x45) | peer → distributor | terminal status code |

A receiver writes a `MSG_FW_CHUNK` only when it arrives over the transport (mesh or BLE) that opened the session, its `sourceMac` is the sender of the OFFER it accepted, over BLE it comes over the connection that sent that OFFER (every app claims the same `sourceMac`), and its offset, length and alignment fit the session (`checkFwChunk`, `components/network/protocol/fw_ota.hpp`). A chunk from any other transport or source is dropped before it touches the partition, the chunk bitmap or the no-progress watchdog, so a sender whose session already ended on the receiver's side cannot write into the next sender's image. A `MSG_FW_DONE` from anyone but that sender is dropped the same way and the session streams on (`fromFwSessionSender`, same header): a mesh sender is matched by `sourceMac`, an app by its BLE connection. `MSG_FS_CHUNK` and `MSG_FS_DONE` follow the same rules.

`MSG_FW_OFFER` is 56 bytes fixed body plus an **additive 96-byte auth trailer** (`FW_OFFER_AUTH_SIZE == 152`): `[56] digest[32]` / `[88] signature[64]`. The signed image's full 32-byte SHA-256 digest + the 64-byte ed25519 signature from the LSIG footer. The receiver ed25519-verifies sig-over-digest against `kFirmwarePubkey` **at offer time, before accepting or erasing** — an unsigned / foreign-key / tampered offer (or a legacy offer with no trailer) is declined with `FwAcceptStatus::DeclineUnverified` and nothing streams. This stops the loop where an unverifiable image streamed in full only to fail end-of-stream verify. The trailer is additive (no `PROTOCOL_VERSION` bump): a pre-trailer sender emits only the 56-byte body and a pre-trailer receiver stops parsing at byte 56, keeping its end-of-stream verify as the gate. The distributor refuses to enable OTA unless its own running image self-verifies against `kFirmwarePubkey` at boot, so an unsigned lamp never offers, and a lamp whose running image is not yet marked valid after an update offers nothing until it is (see [`embedded-heap.md`](embedded-heap.md#rollback-after-an-update)). Post-stream, `verifyAndApply` binds the streamed image's computed digest to the offered (verified) digest, so a source can't offer one image and stream another.

The **FS-image OTA** (`MSG_FS_*`, the SPIFFS web-UI image) reuses this receiver/distributor engine and every MSG_FW_* frame layout, distinguished only by its own msgType IDs: `MSG_FS_OFFER` (0x46), `MSG_FS_ACCEPT` (0x47), `MSG_FS_CHUNK` (0x48), `MSG_FS_REQ` (0x49), `MSG_FS_DONE` (0x4A), `MSG_FS_RESULT` (0x4B). An older lamp that doesn't recognize these drops them as an unknown msgType (no `PROTOCOL_VERSION` bump). It carries the **same 152-byte auth trailer**: the offer's `digest` is the FS manifest digest and `signature` is the `fw.lsig` ed25519 signature over it (same key as firmware). The receiver ed25519-verifies the offer **before** it unmounts SPIFFS and erases the live web UI, so a forged FS offer can't wipe the UI ahead of the post-write verify — the signature is the FS erase-DoS boundary. A pre-trailer (56-byte) FS offer has no signature and is declined. Post-write, `fsVerify` binds the recomputed manifest digest to the offered digest before trusting the embedded signature. The FS OFFER channel field is the unauthenticated wire channel (`fw.lsig` has no channel), so it guards accidental cross-variant seeding, not forgery. Like firmware, FS offer-auth is a static signature over the digest with no replay nonce; a replayed authentic FS offer just re-offers the real image.

See `software/lamp-os/src/components/firmware/` (distributor + receiver) and [`../../scripts/README.md`](../../scripts/README.md) for the signed-image OTA model.

### A/B slots and USB re-flash

The lamp partitions two app slots (`ota_0`/app0, `ota_1`/app1) plus an `otadata` partition that selects which one boots. Each mesh OTA writes the *inactive* slot and flips `otadata` (app0↔app1 ping-pong). The USB flash tasks (`lamp:flash`, `lamp:flash:release`) only ever write **app0** — so a lamp that last OTA-booted app1 keeps booting the stale app1 and the flash lands invisibly in app0. Both tasks therefore erase `otadata` after the write (offset/size read from `partitions.csv`), which makes the 2nd-stage bootloader default back to `ota_0`. `otadata` is separate from `nvs`, so name/config survive. The **web installer** (update.lamplit.ca / `manifest_*.json`) is immune without a reset: it flashes the whole merged image at offset 0, and `esptool merge-bin` leaves the `otadata` region 0xFF, which the bootloader reads as "boot `ota_0`". It also carries `new_install_prompt_erase`, so the web path wipes NVS/name — unlike `lamp:flash:release`, which preserves it. The **wisp** never receives mesh OTA, so its `otadata` never flips and its USB flash needs no reset.

### RSSI gate

`MSG_FW_OFFER`/`MSG_FS_OFFER` are single-hop unicast (no relay), so a weak direct link thrashes or fails a transfer regardless of chunk size. Both sides gate on `kOtaMinRssiDbm` (`components/network/protocol/fw_ota.hpp`, currently -92 dBm): the distributor (`considerPeerForOta`) skips offering below the floor using the RSSI of the peer's own direct HELLO (`LampRoster::espnowRssi`, distinct from the BLE-scan `lastRssi`). A relayed copy of that HELLO measures the relayer's link, so it never writes `espnowRssi` (`helloRosterRssi`, `components/network/mesh/proximity.hpp`): a stored direct reading stands, and a peer heard only by relay reads -127; the receiver (`MeshLink::handleRecv`) independently drops an inbound OFFER whose frame RSSI is below the floor. The -127 "unknown RSSI" sentinel is never gated (allow). This is local, not on the wire — no `PROTOCOL_VERSION` involvement. Gating a weak direct hop doesn't strand a peer: cascade OTA still reaches it later via a nearer already-upgraded lamp.

### Serve-once coordination

A legacy receiver erases + accepts on every fresh `MSG_FW_OFFER`, so two distributors offering the same peer concurrently stomp each other and the transfer never completes. Before offering, the distributor skips a peer the mesh already shows as being served: the peer's own `HELLO_TLV_OTA_STATE` reads receiving, or some roster peer reports `HELLO_TLV_OTA_STATE` = sending with `HELLO_TLV_OTA_SENDING_TO` == that peer. The caller (`tickOtaOffers`, `components/firmware/ota_offer.cpp`) computes this from the roster (which holds peers only, so a lamp never counts its own in-progress send) and passes it to `considerPeerForOta`. Local, roster-derived — no wire change.

### Offer scan and the inter-session hold

`tickOtaOffers` (`components/firmware/ota_offer.cpp`) runs in `Lamp::tick` on every variant once the compositor's startup phase has ended, at most once a second (`OtaOfferThrottle::kIntervalMs`). It walks the ESP-NOW roster and calls `considerPeerForOta` and `fs_ota::considerPeer` per peer, unless the running image is not yet marked valid after an update, an OTA is moving in either direction for either image, a reachable peer runs newer firmware (receive-first), or OTA quiet mode is held. One quiet holder is exempt: after a session that entered quiet ends, the distributor keeps its quiet for `InterSessionQuietHold::kHoldMs` (10 s, `components/firmware/inter_session_quiet_hold.hpp`). When that session ended Done, the scan runs during the hold, so the next offer arms inside it and inherits its quiet, and the indicator stays up through a successful wave instead of flashing back to normal between sessions. The exemption needs the distributor to be the sole holder (`ota_quiet_mode::holders()` is 1 and `FirmwareDistributor::holdingIdleQuiet()`, which is true only for a hold armed by a Done session); quiet from a received OTA, a BLE-pushed OTA or an FS session still blocks the scan. A session that failed or timed out arms a hold the scan does not run through, so its quiet ends 10 s after it as before, and a crowd of peers that never accept cannot keep the lamp quiet. While the exempt hold runs the scan skips the FS walk, since an FS session armed inside it would inherit the firmware session's visible indicator. The gates are `offerBusy` and `OtaOfferBusy::fsWalkAllowed` in `ota_offer.hpp`, pure and natively tested, including a simulated wave of peers that never accept.

### BLE radio pause during a mesh OTA

A mesh OTA in either direction enters quiet mode with the radio torn down (`ota_quiet_mode::enterQuiet`): `ble_control::pauseRadioForOta` stops BLE advertising and the central scan, then `disconnectGattClientsForOta` kicks the connected phone, and once the transition lock is released `webapp::shutdownForOta` takes the web config softAP down on the pausing task, so the chunk stream has the 2.4 GHz radio to itself. `ble_control::resumeRadioAfterOta` on the last quiet exit is the only thing that brings advertising and the scan back. The softAP comes back from `webapp::tick` on the loop, once `ota_quiet_mode::radioTornDown()` reads false, if the pause took it down and the web app would still keep it up: a served page (BLE is down for it) always, otherwise only inside its boot window or idle deadline, or with the window set to never expire (`OtaApFollower`, `apWantedAfterOta` in `components/webapp/webapp_deadline.hpp`, natively tested). An AP that was down at the pause stays down. The loop's own teardowns (a phone connecting over BLE, the boot window ending) and the pausing task's claim the teardown (`SoftApState`, natively tested), so exactly one caller stops mDNS and the AP, and the pause owes the AP back only when its own claim took it down. A lamp with a station on its softAP offers neither image (`OtaOfferBusy::webClient` in `components/firmware/ota_offer.hpp`, natively tested), so an open page is not cut off by this lamp starting a send; an AP with no station holds nothing. A phone that joins after the offer went out, inside the accept window (`kAcceptTimeoutMs`, up to 15 s), does not stop the send: the AP drops for the transfer and the restore above brings it back. Each loop pass does its AP work (the restore, the server start a join asks for, the reboot a station leaving arms, the idle BLE-restore reboot, the BLE-connect reclaim and the boot-window teardown) under the lock `shutdownForOta` takes, so the pausing task's teardown never lands mid-pass: it waits for the pass's AP work to finish, and a pass that finds the lock held skips its AP work and looks again on the next. Station join and leave flags from around the pause are dropped, so a stale join cannot start the server and take BLE down. A served page whose AP cannot be started again reboots the lamp, since it has neither AP nor BLE. A received firmware image reboots before the loop runs again, so its AP is never restarted. Each 0/1 transition of the quiet count runs together with its pause or resume under one lock, so a receiver's last exit racing a distributor's first entry on another task cannot resume the radio under the new send. `BleRadioGate` (`components/network/ble/ble_radio_gate.hpp`, natively tested) owns that rule: it holds the OTA pause and the connected-GATT-client scan hold, and after boot every advertising or scan start the firmware makes goes through it (GATT disconnect, NimBLE scan end, the Social-view scan windows, the rename re-advertise). Each call is serialized, so a disconnect or scan end racing the pause from the NimBLE host task cannot restart the radio under it. NimBLE's own restart on disconnect is off (`advertiseOnDisconnect(false)`); outside a pause the gate restarts advertising on every disconnect. A phone link that completes after the pause's kick ran (the controller accepted it just before advertising stopped) is refused by `BleRadioGate::clientConnected`, and `onConnect` drops it. A NimBLE host reset re-sync restarts advertising inside the library, so `ble_control::tick` calls `BleRadioGate::enforcePause`, which stops it again while the pause holds, and `resumeAfterOta` skips its advertising start when advertising is already on. Known limit: from that re-sync to the next `ble_control::tick` (up to one loop pass, which can last seconds while the receiver runs `verifyAndApply`) the lamp advertises under the pause, and a phone that connects in that window is dropped by the refusal above. A re-sync landing between the resume's check and its start still logs `Advertising already active`, harmlessly. A BLE-pushed OTA keeps the radio up, since the phone is the transport.

Known limits of the pause:
- `BleRadioGate`'s mutex is held across NimBLE calls, which can block up to 2 s on a controller fault; the NimBLE host task's connect, disconnect and scan-end callbacks wait behind it. `s_transitionMu` is held across the same calls (the pause and the resume), so a quiet transition on the loop that collides with the distributor's first entry waits for them too.
- The distributor's streaming task runs `shutdownForOta` before chunk 0, and it waits behind a loop pass's AP work. A pass that starts the server for a phone that just joined takes BLE and its controller down first, so the first chunk can wait for that.
- The offer gate counts any joined station as a web client, open page or not. A phone that auto-joins a remembered lamp network holds that lamp's offers while it stays joined. With no page activity the idle timeout (`LAMP_WEBAPP_IDLE_TIMEOUT_MS`) reboots the lamp to bring BLE back, whatever the Web Config window is set to, and a phone that rejoins after each reboot keeps holding them.

### Channel promotion

A beta lamp graduates to stable via OTA when a stable-channel distributor with a version >= the beta peer's version is present. The decision is one-directional: beta accepts stable, stable never accepts beta. The `{type}` prefix (`standard`, `snafu`) must match exactly at every checkpoint; cross-variant OTA is always rejected.

Three checkpoints gate each transfer:

1. **Distributor offer** (`considerPeerForOta`): calls `otaAcceptable(peerChannel, peerVersion, ourChannel, ourVersion)` — answers "would the peer accept our firmware?" Stable distributor at equal version offers to beta peer; beta distributor never offers to stable peer.
2. **Receiver accept** (`onOfferOnLoop`): calls `otaAcceptable(ourChannel, ourVersion, offerChannel, offerVersion)` — answers "should we accept this offer?" Beta lamp accepts stable offer at `offerVersion >= ourVersion`; stable lamp rejects beta offer unconditionally.
3. **Boot-flip type-gate** (`verifyAndApply`): re-checks the verified LSIG footer channel before setting the boot partition. Uses `otaAcceptable(ours, 0, footerChannel, 1)`; the `0 < 1` version pair satisfies both the intra-channel (`>`) and promotion (`>=`) rules, so a same-channel or beta→stable footer passes while a cross-variant or wrong-suffix footer is rejected.

No protocol bump is required: channel (`HELLO_TLV_FW_CHANNEL`) and version (`firmwareVersion` in the HELLO body) already ride existing v0x05 HELLO fields. The `MSG_FW_OFFER` wire format already carries the 16-byte channel field. The promotion decision is purely local gating on already-available information.
